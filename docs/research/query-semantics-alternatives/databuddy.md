# Databuddy Query Semantics

Sources were checked on **2026-08-23**. Implementation claims below use the vendored Databuddy snapshot at commit [`d15fcb5`](https://github.com/databuddy-analytics/Databuddy/commit/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3), committed 2026-08-21. Only Databuddy's official documentation and source are cited.

## Bottom Line

Databuddy exposes a typed, named-query API rather than one fully general analytics grammar. A request selects one or more query builders, supplies a date range or preset, optional filters/grouping/sort/pagination, and receives one result per parameter. The builder owns metric definitions, allowed dimensions, default ordering, and default limits.

For Cimi, the strongest ideas to borrow are explicit named metrics, server-enforced field/operator allowlists, per-query metadata, and a separate public-read allowlist. The main semantics to avoid copying without clarification are inclusive date ends, offset pagination, and inconsistent visitor identity keys between event families.

## Evidence

### Time Windows And Ranges

- The REST contract requires both `startDate` and `endDate` unless a `preset` is supplied. It supports per-parameter `start_date`/`end_date` overrides inside a multi-query request. ([official query docs](https://www.databuddy.cc/docs/api/query), [request schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/api/src/schemas/query-schemas.ts))
- Presets are timezone-aware at date resolution. The source defines `last_7d` as today minus six days through today, `this_week` as Sunday through today, and `last_week` as the preceding Sunday-to-Saturday week. ([date preset source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/lib/date-presets.ts))
- Standard builders generally use `time >= start` and `time <= end 23:59:59`; the shared builder explicitly appends `23:59:59` unless a builder opts out. This is an **inclusive** calendar-date end, not Cimi's proposed half-open interval. ([standard builder source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/query/simple-builder.ts#L1041-L1061), [summary builder source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/query/builders/summary.ts#L75-L98))
- The public docs state: `"hourly" - Group by hour (max 30 day range)`. The route enforces this when the requested granularity is hourly, using `ceil((to - from) / 1 day) > 30`. ([official query docs](https://www.databuddy.cc/docs/api/query#granularity), [route source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/api/src/routes/query.ts#L838-L855))
- Explicit timestamps with offsets are normalized to UTC text before query execution; date-only values remain date-only until the query builder pads or appends the time boundary. ([date utility source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/date-utils.ts), [finalization source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L608-L669))

### Granularity And Buckets

- The public Query API exposes `daily` and `hourly`; hourly is the default-limited high-resolution mode. `events_by_date` advertises hour/day support and uses `toStartOfHour` or `toDate` for its bucket, ordering the output ascending by bucket. ([official query docs](https://www.databuddy.cc/docs/api/query#granularity), [events-by-date source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/query/builders/summary.ts#L188-L244), [implementation](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/summary.ts#L246-L340))
- The lower-level query type supports `minute`, `hour`, `day`, `week`, and `month`, and the compile endpoint accepts those units. The dynamic public request schema and route normalize only `hourly`/`hour` and `daily`/`day` to hour/day. ([query types](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/types.ts#L1-L1), [compile schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/schemas/query-schemas.ts#L72-L91), [route mapping](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/routes/query.ts#L838-L855))
- The separate dashboard guide says weekly and monthly views exist, while the Query API page lists only daily/hourly. This is a documentation/API-surface mismatch, not a safe assumption for Cimi's canonical contract. ([official dashboard guide](https://www.databuddy.cc/docs/dashboard#data-granularity), [official query docs](https://www.databuddy.cc/docs/api/query#granularity))

### Metrics And Unique Counts

- `summary_metrics` defines pageviews as `countIf(event_name = 'screen_view')`, total events as `count()`, sessions as session groups with at least one screen view, and bounce rate as sessions with exactly one pageview, duration under 10 seconds, and no engagement events. ([summary builder source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/query/builders/summary.ts#L5-L56), [SQL definition](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/summary.ts#L104-L130))
- In that same builder, `unique_visitors` is `uniq(if(event_name = 'screen_view', anonymous_id, null))`. `top_pages` similarly counts `COUNT(*)` pageviews and `uniq(anonymous_id)` visitors after filtering to `screen_view` and grouping by normalized path. ([summary SQL](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/summary.ts#L119-L128), [top-pages builder](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/pages.ts#L6-L35))
- Session-oriented builders use `uniq(session_id)` for sessions and `uniq(anonymous_id)` for visitors. Custom-event builders instead use `coalesce(nullIf(profile_id, ''), nullIf(anonymous_id, ''))`, so an identified profile can deduplicate across devices while rows missing both IDs do not count as a person. ([session builders](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/sessions.ts#L56-L142), [identity keys](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/db/src/clickhouse/identity.ts), [custom-event builder](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/custom-events.ts#L41-L100))
- The official dashboard guide paraphrases the visitor metric as “Unique visitors (deduplicated by anonymous ID)” and sessions as having a 30-minute timeout. The source confirms the anonymous-ID aggregation, but the reviewed query builders do not themselves define the SDK/session timeout. ([official dashboard guide](https://www.databuddy.cc/docs/dashboard#key-metrics), [summary builder source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/query/builders/summary.ts#L104-L123))

### Filters And Dimensions

- Filters are typed as `{ field, op, value }`. The documented operators are `eq`, `ne`, `contains`, `not_contains`, `starts_with`, `in`, and `not_in`; `in`/`not_in` take arrays. ([official query docs](https://www.databuddy.cc/docs/api/query#filter-operations), [request schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/api/src/schemas/query-schemas.ts#L16-L32))
- The shared builder has global filter fields such as `path`, `country`, `region`, `city`, `device_type`, `browser_name`, `os_name`, `referrer`, and UTM fields. Each query builder adds its own allowlist; unsupported filters are removed by the API for that query in a multi-query request, and the remaining conditions are joined with `AND`. ([filter allowlists](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/ai/src/query/simple-builder.ts#L49-L80), [route filtering](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/routes/query.ts#L1019-L1063), [filter SQL](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L1070-L1097))
- Request `groupBy` is limited to an explicit dimension allowlist including geography, technology, path, date, referrer, UTM fields, and selected error/engagement fields. A requested group-by list overrides the builder's configured group-by list; a time bucket is added automatically when the builder declares one. ([group-by validation](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L83-L109), [group-by compilation](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L1100-L1122))
- Filters can target a CTE or be marked as `having`, so the source distinguishes row filters from aggregate-result filters. ([filter type](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/types.ts#L72-L78), [CTE/having handling](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L842-L906))

### Sorting And Pagination

- The documented API uses `limit` and one-based `page`; the default limit is 100 and the maximum is 10,000. The route converts page numbering to `offset = (page - 1) * limit`. ([official query docs](https://www.databuddy.cc/docs/api/query#pagination), [pagination validation and mapping](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/api/src/routes/query.ts#L290-L303), [query preparation](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/routes/query.ts#L1044-L1066))
- The request schema supports `sortBy` and `sortOrder` (`asc`/`desc`). Standard builders allow only a fixed metric/date list and default direction to descending when an order string has no direction; builder defaults commonly rank by visitors or pageviews descending, while time series commonly use date ascending. ([request schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/schemas/query-schemas.ts#L49-L70), [sort allowlist](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L111-L126), [sort compilation](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/simple-builder.ts#L1124-L1141))
- Pagination is offset-based, not cursor-based. The dynamic response metadata reports `page`, `limit`, and `filters_applied`, but no total-row count or cursor. Custom SQL builders may implement their own `LIMIT`/`OFFSET` behavior, so pagination is not perfectly uniform across query types. ([response metadata](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/routes/query.ts#L1161-L1170), [entry-page SQL example](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/pages.ts#L171-L197))

### Public And Shared Analytics

- Databuddy has a public dashboard URL, `/public/{websiteId}`. Its settings UI describes it as: “Anyone with the link can view a read-only public analytics page,” and says visitors cannot access settings, private analytics sections, or delete the site. ([public-sharing UI](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/dashboard/app/%28main%29/websites/%5Bid%5D/settings/general/page.tsx#L321-L378), [public dashboard page](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/dashboard/app/public/%5Bid%5D/page.tsx))
- At the API layer, an unauthenticated request is allowed only when the website is public **and every requested query type** has `publicAccess: true`. The public registry includes overview, custom-event, error, and web-vitals families; revenue builders are explicitly not public in the accompanying source test. ([access check](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/apps/api/src/routes/query.ts#L518-L547), [public query registry](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/index.ts#L39-L145), [public-access test](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3/packages/ai/src/query/builders/public-access.test.ts#L78-L105))
- The official docs make query-type discovery public (`GET /v1/query/types`), but protected query operations normally use an API key or signed-in session. Public website analytics is therefore an explicit website/query-type policy, not a general anonymous analytics API. ([official query docs](https://www.databuddy.cc/docs/api/query#get-query-types), [official authentication docs](https://www.databuddy.cc/docs/api/authentication))

## Cimi Takeaways

- Use named query definitions with explicit output fields and metric descriptions; do not infer semantics from display labels such as “visitors.”
- Prefer UTC instants with `from` inclusive and `to` exclusive, and reject reversed or overlong ranges explicitly. Databuddy's source does not show a start-before-end validation check in the reviewed route.
- Make the identity key part of each metric definition. Cimi should decide whether visitor counts are anonymous-device counts, identified-person counts, or a documented coalescing policy; Databuddy uses more than one policy.
- Keep filters and dimensions query-specific and server-allowlisted. Decide whether an unsupported filter is an error, as Cimi's current convention says, rather than silently dropping it as Databuddy's multi-query route does.
- Prefer stable cursor pagination with a deterministic tie-breaker for canonical resources. If analytics tables require offset pagination, document its snapshot/consistency limitations and return a total or explicit “more” signal.
- Model public analytics as a separate aggregate disclosure contract with an allowlist. Databuddy's public-query registry is a useful precedent; do not make authenticated query types public by default.

## Unknowns And Caveats

- The reviewed route does not visibly reject `startDate > endDate`; the resulting behavior is not established by the official docs/source reviewed.
- The official dashboard guide claims weekly/monthly granularity, but the public Query API documents and route-normalizes only daily/hourly. The authoritative product surface for those modes is unclear.
- The docs describe “visitors” broadly, but visitor identity differs: standard website summaries/pages use `anonymous_id`, while custom events coalesce `profile_id` and `anonymous_id`. Cross-query comparability is therefore not guaranteed.
- No stable cursor, snapshot token, or total-row contract was found for dynamic query pagination.
- The reviewed materials do not establish whether public sharing uses a revocable signed token beyond the website's persisted `isPublic` flag, nor whether all public query types are intended to remain stable API guarantees.
