# Matomo: OLTP/OLAP Boundary and Operational Semantics

Research for Cimi wayfinding issue #24. Researched 2026-08-23. This note is
limited to Matomo's official documentation and official source repositories.
It does not evaluate other products.

## Scope and evidence

The local source checkout reports Matomo `6.0.0-b1`:
`docs/research/vendor/matomo/core/Version.php:25`. Source links below use the
official moving `6.x-dev` or `5.x-dev` branches where noted. The official
developer pages inspected are labelled v5. The version mismatch is material,
especially for optional plugins and operational defaults.

The local checkout does not include the optional QueuedTracking plugin. Queue
behavior is therefore sourced from the official
[`matomo-org/plugin-QueuedTracking`](https://github.com/matomo-org/plugin-QueuedTracking)
repository and Matomo's official QueuedTracking FAQ.

Evidence labels:

- **Fact:** directly documented, implemented, or asserted by the cited source.
- **Inference:** a Cimi interpretation of those facts.
- **Unavailable:** not established by the inspected primary sources.

## Executive assessment

**Fact:** Matomo is a single logical MySQL/MariaDB data system with multiple
table families, not a physically separate OLTP database plus OLAP database.
The same schema contains site and site-setting state, users and permissions,
sessions/options, raw tracking logs, and archive tables
(`core/Db/Schema/Mysql.php:104-160,197-307,309-375`). Matomo's official
architecture guide describes the same model: tracking writes raw `log_*`
data, and archiving later aggregates it into report data.

**Fact:** Raw log tables are optimized for tracking inserts. Report data is
stored separately in `archive_numeric_*` and `archive_blob_*` tables and is
read by report APIs and the UI. The archive schema stores the site, period,
archive timestamp, and a completion marker alongside numeric or serialized
report values (`core/Db/Schema/Mysql.php:309-375`; `ArchiveWriter.php:24-75`).

**Inference:** Matomo's OLTP/OLAP boundary is a logical table and processing
boundary inside one operational database. Cimi's SQLite acceptance journal
plus DuckDB projection is a stronger physical separation: it can isolate
ingestion durability and OLAP workload, but it must explicitly own the
projection checkpoint and rebuild contract that Matomo's archiver provides.

**Fact:** Matomo has two possible tracking acceptance boundaries:

1. The normal tracker writes directly to raw log tables before it formats the
   tracking response.
2. QueuedTracking can first store the request in Redis or a MySQL queue and
   process it later in batches.

**Inference:** A successful HTTP response is not one universal "durably in the
   final analytics tables" acknowledgment in Matomo. Its meaning depends on
   whether QueuedTracking is active. Redis-backed queued acceptance also has a
   documented crash-loss caveat. Cimi should keep its external acceptance
   contract tied to a durable SQLite transaction rather than to an optional
   transport buffer.

## Data and write paths

### Canonical operational state

**Fact:** Matomo's schema stores website identity and reporting configuration
in the same database as tracking data. Examples include `site`, `site_setting`,
`site_url`, `goal`, `option`, `session`, and access-control tables
(`core/Db/Schema/Mysql.php:104-184,291-307`).

**Fact:** Raw tracking is represented by several related tables:

- `log_visit`: one visit row with site, visitor, configuration, and timing data.
- `log_action`: the action dictionary.
- `log_link_visit_action`: one row for a visitor action.
- `log_conversion` and `log_conversion_item`: conversion data.

The core schema defines these tables and their indexes at
`core/Db/Schema/Mysql.php:197-279`. Matomo's official architecture guide says
these tables are designed for fast tracking inserts.

**Fact:** The visible standard tracker selects or creates visit/action state,
then the model executes a plain `INSERT` into
`log_link_visit_action` (`core/Tracker/Model.php:22-43`). The standard handler
iterates request sets and calls `trackRequest` for each request
(`core/Tracker/Handler.php:47-57`).

**Fact:** The normal action primary key is generated by Matomo. The inspected
write path has no caller-supplied event ID or unique constraint covering the
visitor, visit, timestamp, and event dimensions. Existing event/session
research records this at `docs/research/event-session-alternatives/matomo.md:244-256`.

**Inference:** Replaying an accepted normal tracking request can create another
action row. Matomo's visible tracking contract does not establish exactly-once
delivery or application-level idempotency.

### HTTP acknowledgment

**Fact:** Matomo's Tracking HTTP API accepts GET or POST requests. With
`send_image=0`, the response is HTTP 204 rather than a tracking image
([Tracking HTTP API](https://developer.matomo.org/api-reference/tracking-api)).
The local response implementation emits 204 when that parameter is present
(`core/Tracker/Response.php:128-157`).

**Fact:** In the normal handler, tracking processing runs before
`finish()` formats the response (`core/Tracker.php:112-140`; `core/Tracker/Handler.php:111-115`).
The visible code therefore places the database write path before response
formatting.

**Unavailable:** The inspected public documentation does not define HTTP 200
or 204 as a durable, fsync-level acknowledgment, and the normal tracker files
do not show one explicit transaction around every request. Storage-engine
autocommit, database durability settings, and crash behavior remain deployment
concerns.

### Bulk tracking

**Fact:** BulkTracking can wrap a request set in a database transaction. The
checkout enables this by default with `bulk_requests_use_transaction = 1`
(`config/global.ini.php:1101-1106`). The bulk handler begins before processing,
commits after all requests, and rolls back on an uncaught exception
(`plugins/BulkTracking/Tracker/Handler.php:33-43,47-81`).

**Fact:** Invalid request parameter and unknown-site exceptions are collected as
invalid indexes rather than automatically aborting the entire bulk request
(`plugins/BulkTracking/Tracker/Handler.php:55-75`).

**Inference:** Bulk tracking gives Matomo a useful batch atomicity mode for
valid database writes, but it is not an event-level idempotency contract and
does not make the raw-to-archive boundary synchronous.

## QueuedTracking boundary

**Fact:** The official QueuedTracking plugin replaces the normal tracker
handler when enabled. It writes request sets to Redis or a MySQL queue instead
of directly to the Matomo log tables
([plugin README](https://github.com/matomo-org/plugin-QueuedTracking/blob/5.x-dev/README.md);
[plugin handler selection](https://github.com/matomo-org/plugin-QueuedTracking/blob/5.x-dev/QueuedTracking.php)).

**Fact:** Matomo's official FAQ describes the queue as temporary storage. A
worker takes requests in batches and inserts them into Matomo. The FAQ says the
MySQL backend creates `queuedtracking_queue` tables, while Redis is faster but
queued requests are lost if the Redis server crashes
([QueuedTracking FAQ](https://matomo.org/faq/on-premise/how-to-use-the-queuedtracking-plugin/)).

**Fact:** The official queue source serializes a `RequestSet`, appends it to a
backend list, reads the first configured batch, and exposes a separate
operation to remove the first batch (`Queue.php` at the pinned
[official source revision](https://github.com/matomo-org/plugin-QueuedTracking/blob/d13a9ecaf1638be125330bcc796cdd8fcac61f13/Queue.php)).

**Fact:** Matomo recommends disabling processing during tracking requests and
running `queuedtracking:process` from cron for multiple servers. The official
FAQ also documents queue workers, batch size, queue monitoring, and queue
locking.

**Inference:** QueuedTracking changes the meaning of a successful tracking
response from "the final raw log write completed" to something closer to
"the configured queue accepted the request," subject to backend durability.
This is an operationally useful smoothing mechanism, not a replacement for a
durable event journal with a stable acknowledgment and replay contract.

**Unavailable:** The reviewed official materials do not provide a complete
cross-backend contract for crash recovery, dead-letter handling, per-request
retry counts, or exactly-once behavior. The Redis loss caveat is explicit; the
MySQL queue's complete failure and recovery semantics are not.

## Archive and query boundary

### Archiving

**Fact:** Matomo's official architecture documentation says the archive process
reads raw log data and produces report data because aggregating large log tables
for every report would be too expensive. Numeric metrics are stored in
`archive_numeric_*` tables and serialized report tables in
`archive_blob_*` tables
([How Matomo Works](https://developer.matomo.org/guides/how-piwik-works);
[Archive data](https://developer.matomo.org/guides/archive-data)).

**Fact:** The local archive writer marks an archive as incomplete before work,
marks it complete after work, and supports invalidated states
(`core/DataAccess/ArchiveWriter.php:24-75`).

**Fact:** Archive invalidation is deferred. Matomo's source explicitly says
invalidated archive data can remain visible in the UI and API until cron or
browser-triggered archiving reprocesses it
(`core/Archive/ArchiveInvalidator.php:34-56`).

**Fact:** In the local defaults, today's archive is considered outdated after
900 seconds, browser archiving is enabled, and archive jobs have a 24-hour
failure-recovery timeout (`config/global.ini.php:372-405`). These are defaults
and can be overridden in the UI or deployment configuration. Current official
high-traffic guidance recommends cron archiving hourly with a one-hour archive
freshness setting
([high-traffic guidance](https://matomo.org/faq/on-premise/running-matomo-in-high-traffic-environments/)).

**Inference:** Matomo reports are intentionally eventually consistent with raw
tracking. A report can be validly served while stale, and a raw-data mutation
can require explicit archive invalidation and reprocessing before derived
reports reflect it.

### Retention and deletion

**Fact:** Matomo distinguishes raw data from report data. On-Premise can retain
both indefinitely, while its privacy controls allow separate policies for raw
logs and aggregated reports
([data retention FAQ](https://matomo.org/faq/general/configure-data-retention/)).

**Fact:** The raw-log purger deletes old visit/action/conversion data, including
`log_visit`, `log_link_visit_action`, `log_conversion`,
`log_conversion_item`, and optionally unused `log_action` rows
(`plugins/PrivacyManager/LogDataPurger.php:22-101`).

**Fact:** The report purger independently removes old numeric and blob archive
data while preserving configurable basic metrics, periods, or segments
(`plugins/PrivacyManager/ReportsPurger.php:19-155`).

**Fact:** Specific Visit deletion and historical report reprocessing are
separate from age-based purging. Existing Matomo research records that this
requires the raw Visit details to remain available:
`docs/research/visitor-identity-alternatives/matomo.md:48-53`.

**Inference:** Matomo demonstrates why Cimi should model raw-event retention,
derived-report retention, and deletion completion separately. Deleting the
SQLite journal while keeping DuckDB aggregates would preserve query results but
remove rebuild capability; deleting only DuckDB would preserve rebuildability
but create a freshness gap until projection catches up.

## Backup and recovery boundary

**Fact:** Matomo's official backup guidance treats the database and application
files as separate backup inputs. The database contains Matomo data, while
`config/config.ini.php` and installed plugins/code also need backup
([backup data and files](https://matomo.org/faq/how-to-install/faq_138/)).

**Fact:** Matomo documents a full MySQL/MariaDB dump using `mysqldump` with
`--single-transaction`, and recommends a read replica or physical backup tool
for larger installations
([backup and restore](https://matomo.org/faq/how-to/how-do-i-backup-and-restore-the-matomo-data/)).

**Fact:** Matomo's official FAQ says partial restoration into an existing
running database is not supported; recovery of selected data requires restoring
the full database into a separate installation
([partial database restore](https://matomo.org/faq/on-premise/is-it-possible-to-restore-partial-data-from-a-database-dump-into-the-matomo-database/)).

**Inference:** A Matomo backup is a multi-artifact recovery procedure, not a
single raw-log snapshot. If QueuedTracking is enabled, the queue backend is an
additional state boundary that must be drained, backed up, or explicitly
accepted as recoverable loss. Matomo's public materials do not define one
atomic checkpoint spanning database, Redis, configuration files, archive state,
and in-flight queue workers.

## Operational topology

**Fact:** Matomo's official high-availability guidance places tracking, UI, and
reporting application servers in front of a MySQL/MariaDB database that stores
all Matomo data. It recommends replication, shared application/config files,
cron archiving, Redis for caching or QueuedTracking, and monitoring queue and
archive lag
([high-availability guidance](https://matomo.org/faq/on-premise/how-to-configure-matomo-for-high-availability-multi-server-environment/);
[high-traffic guidance](https://matomo.org/faq/on-premise/running-matomo-in-high-traffic-environments/)).

**Inference:** Matomo scales by protecting and scheduling access to the central
operational database, not by treating a separate OLAP store as the canonical
write target. Its queue and archive workers are throughput and freshness
controls around that database.

## Implications for Cimi issue #24

1. **Keep the acceptance boundary explicit.** Cimi's accepted event should be
   durably committed to SQLite before the public acknowledgment. A later queue
   or DuckDB projection may be asynchronous, but it must not redefine the
   acceptance guarantee.

2. **Treat DuckDB as a rebuildable projection.** Store a projection checkpoint
   or watermark tied to committed SQLite events. A projection failure should
   leave the journal authoritative and permit replay without relying on
   Matomo-style report invalidation metadata alone.

3. **Expose freshness.** Report responses should make the projection watermark
   or last successful materialization time available when stale data is possible.
   Matomo's archive invalidation behavior shows that a successful report
   response does not imply current raw data has been reflected.

4. **Separate retention policies.** Define independent policy and completion
   semantics for raw SQLite events, DuckDB-derived data, exports, logs, and
   backups. Do not treat deletion of one layer as deletion of the whole
   analytics record.

 5. **Define recovery scope.** DuckDB is rebuilt from SQLite. A derived DuckDB
    copy may accelerate repair, but it is not required for backup correctness.
    The operating envelope must include rebuild duration and query unavailability.

6. **Do not inherit exactly-once assumptions.** Matomo's normal action writes
   lack a caller event ID, and QueuedTracking changes where a request is
   temporarily accepted. Cimi should retain its own event ID and idempotency
   constraint at the SQLite boundary.

## Boundary matrix

| Concern | Matomo location | Authority | Rebuild or repair path | Cimi implication |
| --- | --- | --- | --- | --- |
| Site/configuration state | MySQL/MariaDB tables and config files | Matomo database plus files | Restore database and files | Keep tenant/site state outside analytics projection |
| Accepted tracking request | Raw `log_*` tables, or Redis/MySQL queue when QueuedTracking is enabled | Final authority is raw log data after queue processing | Replay queue or restore DB; exact queue recovery varies | SQLite journal must be the explicit durable authority |
| Derived metrics/reports | `archive_numeric_*`, `archive_blob_*` | Archive rows while valid | Invalidate and re-archive from raw logs | DuckDB rows need a checkpoint and rebuild contract |
| Freshness | Archive timestamps, done flags, invalidations, cron/browser settings | Operational archive state | Re-run archiver | Expose projection freshness and lag |
| Raw retention | PrivacyManager log purger | Raw log policy | Not reversible after deletion without backup | Define journal deletion versus rebuild capability |
| Report retention | PrivacyManager reports purger | Archive policy | Re-archive if raw data remains | Derived retention can be shorter than raw retention |
| Backup | MySQL dump/replica plus config/plugins/files | Operator backup plan | Full restore and validation | Make SQLite authoritative; rebuild DuckDB and validate before readiness |

## Unknowns and verification needs

- Verify all conclusions against the exact Matomo and QueuedTracking releases
  supported by any future integration; the local checkout is `6.0.0-b1`, while
  several official plugin links are `5.x-dev`.
- Establish whether Cimi needs a queue at all. A queue can smooth spikes, but
  it adds an external durability and recovery boundary before the authoritative
  SQLite journal.
- Define the projection freshness SLA and the behavior of queries while a
  projection is behind or rebuilding.
- Define whether deletion completion includes DuckDB, exports, logs, backup
  generations, and queued or in-flight work.
- Define and test the crash points around SQLite commit, projection checkpoint
  commit, DuckDB materialization, backup capture, and restore.
- Matomo's public sources do not establish a universal cross-component atomic
  checkpoint or exactly-once event contract; Cimi should not infer either from
  its archive and queue mechanisms.
