# Plausible Analytics: Visitor Identity Research

## Scope and Version Context

This report covers Plausible's website analytics collection path, not just its dashboard login system. Official pages were checked on 2026-08-22. The data policy says it was last updated in March 2026; the privacy policy says it was last updated in August 2026 ([data policy](https://plausible.io/data-policy), [privacy policy](https://plausible.io/privacy)). Source-code observations use the official repository's `master` commit `9cc669b97ece3ecd37fcb3950791cb3873d7944d`, committed 2026-08-19 ([commit](https://github.com/plausible/analytics/commit/9cc669b97ece3ecd37fcb3950791cb3873d7944d)). The repository still has an `Unreleased` changelog section, so source observations are not necessarily the behavior of the latest numbered self-hosted release ([CHANGELOG](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/CHANGELOG.md)).

## Executive Finding

**Documented fact:** Plausible is designed for anonymous, aggregate reach measurement. It does not give the browser a persistent visitor identifier, does not link visitors across days, devices, or websites, and says that analytics does not require cookie consent ([data policy](https://plausible.io/data-policy), [metrics definitions](https://plausible.io/docs/metrics-definitions), [compliance overview](https://plausible.io/docs/compliance)).

**Implementation fact:** Plausible nevertheless stores server-side event and session rows containing a daily `user_id` and a random `session_id`. Those are processing keys for aggregation and sessionization, not a browser-visible identified-user account ([event ingestion](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/ingestion/event.ex), [session schema](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/clickhouse_session_v2.ex), [ClickHouse schema](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/priv/ingest_repo/structure.sql)).

**Inference for Cimi:** Plausible supplies a useful anonymous `Visitor-on-a-day` and `Session` model, but not a first-class `Identified User` model or a cross-day visitor graph.

## Visitor Identity

### Documented behavior

- **Daily scope:** Plausible says all visitor data is isolated to one day, one website, and one device. A person using multiple devices or returning on multiple days is counted as separate visitors ([data policy](https://plausible.io/data-policy)).
- **Daily key:** The documented formula is `hash(daily_salt + website_domain + ip_address + user_agent)`. Plausible says the salt is rotated and deleted every 24 hours, while raw IP addresses and User-Agent values are not stored ([data policy](https://plausible.io/data-policy)).
- **Inputs:** The Events API documents that the raw User-Agent contributes to `user_id`, and that the client IP contributes to `user_id` and geolocation but is not stored in the database ([Events API](https://plausible.io/docs/events-api)).
- **No durable browser identity:** Plausible says it uses no cookies, browser cache, local storage, or other persistent identifiers for visitor tracking ([data policy](https://plausible.io/data-policy), [compliance overview](https://plausible.io/docs/compliance)).

### Source confirmation and nuance

- **Current source implementation:** `generate_user_id/4` uses SipHash with the current salt over User-Agent, remote IP, the configured site domain, and the request hostname's registrable root domain ([source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/ingestion/event.ex)). This is more precise than the public formula and confirms that the identifier is generated server-side from request inputs.
- **Event-level persistence:** The current schema stores `user_id` in both `events_v2` and `sessions_v2`, and stores `session_id` on events and sessions; it does not define raw IP or raw User-Agent columns ([source schema](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/priv/ingest_repo/structure.sql)). **Inference:** "No persistent identifiers" means no durable visitor identifier exposed to or retained in the browser; it does not mean the server processes no pseudonymous key during ingestion.
- **Previous-salt bridge:** Before session registration, the source computes both the current and previous-salt user IDs. Session lookup tries the current ID and then the previous ID ([event source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/ingestion/event.ex), [session cache source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/session/cache_store.ex)). **Inference:** An active session can remain continuous across a daily salt rotation, but this is session continuity, not cross-day visitor identity.
- **Current-source caveat:** The same source has Enterprise-only (`on_ee`) replay-session fields and includes `replay_session_id` in the hash input; that path is not described by the public standard visitor documentation ([event source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/ingestion/event.ex), [request source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/ingestion/request.ex)). Cimi should not generalize Community Edition behavior to every current Enterprise feature.

## Session Model

- **Definition:** A visit/session starts at the first landing page and ends after 30 minutes without action. One visitor can have multiple sessions on the same day ([metrics definitions](https://plausible.io/docs/metrics-definitions)).
- **Hostname boundary:** The Events API says that two events from the same client for two different hostnames produce two sessions ([Events API](https://plausible.io/docs/events-api)).
- **Server-side session key:** The current source looks up an active session by site plus `user_id`, accepts it only when the latest event is within 30 minutes, and otherwise creates a session with a random `UInt64` `session_id` ([session cache source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/session/cache_store.ex), [session schema](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/clickhouse_session_v2.ex)).
- **Persistence meaning:** Sessions are maintained in an in-memory cache and written to ClickHouse through a write buffer; events are then merged with the session's `session_id` ([persistor](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/ingestion/persistor/embedded.ex), [session cache source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/session/cache_store.ex)). **Inference:** "Session persistence" in Plausible is server-side analytics storage, not a client session cookie.

## Browser Storage and Cookies

- **Analytics tracker:** The current tracker builds a payload from event name, URL, domain, referrer, properties, and configuration, then sends it to `/api/event`; it does not create a visitor cookie or client visitor ID ([tracker source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/tracker/src/track.js), [networking source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/tracker/src/networking.js)).
- **Opt-out/exclusion storage:** The tracker reads `localStorage.plausible_ignore === "true"` and skips the event. The official exclusion instructions require setting this separately for every domain/subdomain and browser ([tracker source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/tracker/src/track.js), [exclusion documentation](https://plausible.io/docs/excluding-localstorage)). **Inference:** This is a locally stored opt-out switch, not an identity mechanism and not a server-side deletion request.
- **Dashboard account is separate:** Plausible's privacy policy says a persistent first-party cookie is used to keep a customer logged in ([privacy policy](https://plausible.io/privacy)). The source stores a dashboard user token in the web session, sets a `logged_in` marker cookie, and gives standard account sessions a 14-day inactivity timeout renewed by activity ([UserAuth source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible_web/user_auth.ex), [user session source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/auth/user_session.ex)). These are dashboard authentication artifacts, not visitor analytics identifiers.

## Identified Users and Linkage

- **No documented first-class identified visitor:** The Events API request has no documented `user_id` or login-identity field; custom properties are event properties attached to pageviews or custom events ([Events API](https://plausible.io/docs/events-api), [custom properties](https://plausible.io/docs/custom-props/introduction)). **Inference:** Plausible does not provide a documented "identify this visitor and stitch all future sessions" operation comparable to an identified-user analytics model.
- **Custom properties are not a safe identity substitute:** Plausible permits segmentation examples such as login status or user role, but prohibits PII including names, usernames, email addresses, IP addresses, and pseudonymous cookie or advertising IDs ([custom properties](https://plausible.io/docs/custom-props/introduction)). Sending an account ID as a custom property would therefore require a separate privacy and re-identification review; it is not an endorsed identity-linking contract.
- **Attribution is intentionally limited:** Plausible documents last-click conversion attribution because it avoids cookies and long-term identifiers. It also strips `gclid` and `msclkid` values while retaining the campaign category ([traffic sources](https://plausible.io/docs/top-referrers)).

## Privacy and Consent

- **Vendor position:** Plausible says it collects no personal data for website visitor analytics, does not track individuals across sites/devices, does not use visitor data for advertising, profiling, or monetization, and keeps visitor data in the EU ([data policy](https://plausible.io/data-policy), [compliance overview](https://plausible.io/docs/compliance)).
- **Consent position:** Plausible says no cookie banner or analytics tracking consent is required because the visitor tracker does not store information on the device ([data policy](https://plausible.io/data-policy), [compliance overview](https://plausible.io/docs/compliance)). This is Plausible's documented compliance position, not a substitute for Cimi-specific legal review or jurisdictional analysis.
- **Data minimization is still required:** Plausible's custom-property documentation forbids PII, and its URL-redaction guidance recommends replacing user-specific identifiers in paths before sending them ([custom properties](https://plausible.io/docs/custom-props/introduction), [custom locations](https://plausible.io/docs/custom-locations)). **Inference:** A cookieless design does not make arbitrary URLs, event properties, or application identifiers safe by default.

## Retention and Deletion Semantics

### Visitor and analytics data

- **Salt lifetime:** Public documentation says the daily salt is rotated and deleted every 24 hours ([data policy](https://plausible.io/data-policy)). The current source keeps current and previous salts available and deletes database salt rows older than 48 hours ([salt manager](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/session/salts.ex), [salt rotation worker](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/workers/rotate_salts.ex)). **Inference:** "Deleted every 24 hours" describes the effective daily identity boundary, while the implementation retains enough salt history to bridge rotation and may physically retain old salt rows longer.
- **Managed-plan retention:** The public plan documentation says data retention is a plan limit and can be increased for Enterprise, but does not state one universal number ([subscription plans](https://plausible.io/docs/subscription-plans)). The current repository's `plans_v5.json` sets `data_retention_in_years` to 3 for Starter/Growth and 5 for Business ([source plan data](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/priv/plans_v5.json)). This is versioned product configuration, not evidence of a self-hosted default.
- **Self-hosted storage:** The current ClickHouse schema partitions event and session tables by month and shows no table-level TTL clause ([source schema](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/priv/ingest_repo/structure.sql)). **Inference:** Cimi should not assume that a database partition automatically supplies a retention policy; an explicit policy and enforcement mechanism are needed.

### Site, account, and reset deletion

- **Delete site:** The docs say deleting a site removes the site and all stats collected to that point ([delete site data](https://plausible.io/docs/delete-site-data)). Current source records a pending deletion, removes the site record, and has an asynchronous worker delete `events_v2`, `sessions_v2`, imported tables, and ingest counters from ClickHouse ([site removal](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/site/removal.ex), [cleanup worker](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/workers/clickhouse_clean_sites.ex)). **Documented/source fact:** completion is asynchronous, not necessarily immediate.
- **Reset stats:** The docs say reset removes stats collected to that point ([reset site data](https://plausible.io/docs/reset-site-data)). The current controller calls `Plausible.Purge.reset!`, which only advances `native_stats_start_at` and clears `stats_start_date`; it does not enqueue the ClickHouse deletion worker ([site controller](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible_web/controllers/site_controller.ex), [purge source](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/plausible/purge.ex)). **Inference:** In this source snapshot, reset is a logical visibility cutoff, not demonstrated physical erasure. Cimi should distinguish "no longer queryable" from "deleted from storage and backups."
- **Delete account:** The docs say account deletion removes all sites and stats ([delete account](https://plausible.io/docs/delete-account)); the privacy policy says account data is permanently deleted without undue delay after account deletion ([privacy policy](https://plausible.io/privacy)). This statement concerns the customer account and associated site data, not an individual visitor's self-service deletion record.
- **Cancellation:** After the paid period, the dashboard is locked; Plausible stops collecting one month after locking and may later delete sites and stats after warning the customer ([cancellation documentation](https://plausible.io/docs/cancel-subscription)). Deleted data cannot be recovered. This is subscription lifecycle retention, separate from the daily visitor-key lifetime.
- **Dashboard login-session cleanup:** Expired account sessions are removed by a worker after a seven-day grace period ([session cleanup worker](https://github.com/plausible/analytics/blob/9cc669b97ece3ecd37fcb3950791cb3873d7944d/lib/workers/clean_user_sessions.ex)). This is not retention of website visitor analytics.

## Implications and Questions for Cimi

- Should Cimi define `Visitor` as a daily, site-scoped anonymous measurement key, or does issue #5 require a durable visitor entity?
- Should `Session` be a server-side aggregate keyed by an ephemeral visitor key with a 30-minute inactivity boundary, with explicit behavior at salt rotation?
- Is `Identified User` a separate authenticated-domain concept, rather than an analytics visitor identity? If linkage is required, what consent, access, and deletion rules govern it?
- What exact fields may enter analytics events, especially URL paths, query parameters, traits, and account identifiers? Which fields must be rejected or redacted before persistence?
- Does "delete visitor data" mean suppress future collection, delete event/session rows, remove aggregates, invalidate salts, remove exports/backups, or all of these? Plausible's site deletion and reset paths show why those meanings need separate contracts.
- What retention period applies independently to raw events, session aggregates, daily salts, logs, exports, and backups, and how is each period enforced for self-hosted installations?
- Is a per-domain/per-browser local opt-out enough for Cimi, or must authenticated users have a server-side opt-out and deletion workflow?
- Can Cimi adopt Plausible's no-consent position for anonymous analytics, or do Cimi's authenticated identities, custom traits, deployment choices, or jurisdictions require a different consent and legal basis?
