# Matomo Visitor Identity and Privacy

Research for Cimi issue #5. Researched 2026-08-22. Sources are limited to Matomo's official documentation, developer documentation, and `matomo-org/matomo` source repository.

## Version Context

- The developer documentation pages are labelled **v5**; several general FAQ pages were published or updated between 2021 and 2026. The exact Matomo release matters for tracker and privacy behavior. [JavaScript API v5](https://developer.matomo.org/api-reference/tracking-javascript) [HTTP API v5](https://developer.matomo.org/api-reference/tracking-api)
- Source references below use the moving [`5.x-dev` branch](https://github.com/matomo-org/matomo/tree/5.x-dev), inspected on 2026-08-22, not a pinned release. Cimi should verify the selected Matomo release before treating implementation details as contractual.
- Statements are documented facts unless marked **Inference**; an inference is a Cimi interpretation of the cited Matomo behavior, not a Matomo-defined concept.

## Canonical Mapping

| Cimi concept | Matomo mechanism | Persistence and meaning |
| --- | --- | --- |
| Visitor | `Visitor ID` / `idvisitor`, a 16-character hexadecimal identifier | Normally held in the first-party `_pk_id` cookie for 13 months by default; the timeout is configurable. **Inference:** this identifies a browser/site relationship, not necessarily a person. [Cookies FAQ](https://matomo.org/faq/general/faq_146/) [HTTP API](https://developer.matomo.org/api-reference/tracking-api) |
| Session | Matomo `Visit` / server-side `idvisit` | A continuous activity session. The default boundary is 30 minutes without a tracked action, with additional campaign and local-midnight boundaries; On-Premise can configure `visit_standard_length`. The `_pk_ses` cookie is supporting session state, not a durable account session. [Visit definition](https://matomo.org/faq/general/faq_36/) [Cookies FAQ](https://matomo.org/faq/general/faq_146/) |
| Anonymous identity | A Visitor ID when cookies are allowed; otherwise short-lived `config_id` matching may group actions | This is an implementation inference, not a Matomo domain object named "anonymous identity." `config_id` is site-specific, time-limited, rotated, and used only within a short lookback window. [Config ID FAQ](https://matomo.org/faq/general/how-is-the-visitor-config_id-processed/) [Visitor matching FAQ](https://matomo.org/faq/general/faq_21418/) |
| Identified user | `User ID` / tracking parameter `uid` | An application-supplied, unique, persistent, non-empty identifier for a logged-in user. It links activity across sessions, browsers, and devices when sent consistently. [User ID setup](https://matomo.org/faq/reports/set-up-user-id-tracking-in-matomo/) [HTTP API](https://developer.matomo.org/api-reference/tracking-api) |
| Trait | Visit/action/conversion Custom Dimension, or legacy Custom Variable | Visit dimensions live on a visit and use the last value set during that visit; action dimensions live on individual actions. Custom Variables are deprecated. **Inference:** neither mechanism is a durable account profile by itself. [Dimensions guide](https://developer.matomo.org/guides/dimensions) [Custom Dimensions FAQ](https://matomo.org/faq/reporting-tools/create-track-and-manage-custom-dimensions/) [Custom Variables FAQ](https://matomo.org/faq/how-to/guide-to-using-custom-variables-deprecated/) |

## Identity and Session Semantics

- Matomo's default web tracker uses first-party cookies on the tracked site's domain. Different domains do not share the cookie by default; cross-domain linking forwards the visitor ID through a short-lived `pk_vid` link parameter, and an optional third-party ID cookie is not enabled by default. [Cookies FAQ](https://matomo.org/faq/general/faq_146/) [JavaScript API v5](https://developer.matomo.org/api-reference/tracking-javascript)
- A Visitor ID is not automatically portable across browsers or apps. Matomo's 2026-08-07 guide recommends User ID for a stable authenticated account; an anonymous handoff requires the application to transfer the Visitor ID and apply `setVisitorId()` before the first request in the new environment. The guide also says to protect the handoff with a short-lived backend token and not expose the Visitor ID in a URL. [Cross-browser/app linking guide](https://matomo.org/faq/how-to/link-visitors-between-different-browsers-and-apps-visitor-user-id/)
- Matomo's official documentation is inconsistent on the persistence of that handoff: the current v5 JavaScript API says `setVisitorId()` is not persisted and must be repeated on each new page load, while the 2026-08-07 cross-browser guide says the transferred ID is stored in a new first-party cookie and reused on later loads. **Documented fact:** both statements exist. **Cimi implication:** pin a Matomo release and run an integration test before depending on the newer behavior. [JavaScript API v5](https://developer.matomo.org/api-reference/tracking-javascript) [Cross-browser/app linking guide](https://matomo.org/faq/how-to/link-visitors-between-different-browsers-and-apps-visitor-user-id/)
- A Visit is not a user-owned session record. Matomo starts a new Visit after the default 30-minute inactivity period, a new campaign source, or the configured site's midnight; a Visitor can have many Visits. The timeout is `1800` seconds by default for On-Premise and can be changed. [Visit definition](https://matomo.org/faq/general/faq_36/) [Matomo default configuration](https://github.com/matomo-org/matomo/blob/5.x-dev/config/global.ini.php)
- A User ID must be set before each tracked pageview/action where it is applicable; when no User ID is available, Matomo tracks anonymously. On logout, Matomo recommends `resetUserId()`. By default, a logged-out continuation can retain the User ID for the rest of the Visit; Cimi can instead reset it and force `new_visit=1` to prevent post-logout actions joining the authenticated Visit. [JavaScript tracking guide](https://developer.matomo.org/guides/tracking-javascript-guide) [User ID request semantics](https://matomo.org/faq/general/how-are-requests-with-a-user-id-tracked/)
- Matomo 4+ defaults to treating concurrent visits carrying the same User ID as one Visit/one unique visitor. On-Premise can disable `enable_userid_overwrites_visitorid`; then two devices are counted as two Visits and two unique visitors even though the User ID is the same. This is a reporting policy choice, not merely a storage detail. [User ID request semantics](https://matomo.org/faq/general/how-are-requests-with-a-user-id-tracked/)
- **Source detail, version-sensitive:** in `5.x-dev`, `Tracker\Request::getVisitorId()` checks an enabled `enable_userid_overwrites_visitorid` setting before a forced `cid`, optional third-party cookie, or first-party cookie; its matching path derives the first 16 hex characters of `sha1($userId)`. This is a visitor-matching implementation path, not proof of anonymization. [Request.php, `5.x-dev`](https://raw.githubusercontent.com/matomo-org/matomo/5.x-dev/core/Tracker/Request.php)

## Cookies and Browser Storage

- Default cookie lifetimes are `_pk_id` 13 months for the Visitor ID, `_pk_ses` 30 minutes for current-Visit state, and `_pk_ref` 6 months for attribution. Matomo exposes JavaScript timeout setters, so these are defaults rather than Cimi retention guarantees. [Cookies FAQ](https://matomo.org/faq/general/faq_146/) [JavaScript API v5](https://developer.matomo.org/api-reference/tracking-javascript)
- Disabling Matomo cookies does not automatically stop tracking. It removes persistent cross-session identity and can reduce report accuracy, while cookieless matching may still process request/device data. `requireConsent` is the stronger control when no tracking request should be sent. [Cookieless FAQ](https://matomo.org/faq/general/faq_157/) [Consent guide](https://developer.matomo.org/guides/tracking-consent)
- Core Visitor/User identity is cookie/request based; Matomo's cookie inventory lists local storage for optional A/B Testing (`MatomoAbTesting`), not as the core Visitor ID store. Visit Custom Variables can optionally be copied into a first-party cookie for the current Visit, but are not durable user storage. [Cookies FAQ](https://matomo.org/faq/general/faq_146/) [JavaScript tracking guide](https://developer.matomo.org/guides/tracking-javascript-guide)

## Privacy and Consent

- Matomo's `requireConsent` mode sends no tracking request and sets no cookies until consent. `requireCookieConsent` still sends tracking requests but does not use cookies until cookie consent. The latter can therefore still collect cookieless analytics and is not equivalent to refusing all processing. [Consent guide](https://developer.matomo.org/guides/tracking-consent) [JavaScript API v5](https://developer.matomo.org/api-reference/tracking-javascript)
- Remembered consent is browser state: Matomo's v5 consent guide says it is remembered forever by default, with an optional expiry in hours; the consent cookie is then used on subsequent requests. `forgetConsentGiven()` or `forgetCookieConsentGiven()` removes the remembered consent and requires consent again. [Consent guide](https://developer.matomo.org/guides/tracking-consent) [JavaScript API v5](https://developer.matomo.org/api-reference/tracking-javascript)
- The opt-out mechanism sets `mtm_consent_removed`; Matomo documents that visitors carrying it are not tracked. **Inference:** opt-out is a forward-processing control, not historical erasure; the documentation does not say it deletes prior server-side Visits, reports, cookies, or logs. [Privacy settings](https://matomo.org/docs/privacy-how-to/) [Cookies FAQ](https://matomo.org/faq/general/faq_146/)
- Matomo identifies User IDs as precise, persistent identifiers that likely require consent. Its pseudonym option uses a deterministic hash plus an installation-specific salt, hides the original value in analytics, and is explicitly **not anonymization**: the pseudonym remains personal data. [User ID privacy](https://matomo.org/faq/reports/user-id-privacy-considerations/) [Privacy settings](https://matomo.org/docs/privacy-how-to/)
- Matomo's consent-exemption guidance treats User ID and other individual-level features as non-exempt in the cited configurations; prior consent is required before enabling them where the jurisdiction requires it. Matomo also notes that ePrivacy interpretations vary by country. [ePrivacy guidance](https://matomo.org/faq/general/eprivacy-directive-national-implementations-and-website-analytics/)
- `config_id` is a privacy-limited fallback, not a durable anonymous account key: Matomo describes it as site-specific, valid for at most 24 hours, rotated daily, and not intended to recognize returning visitors or track across sites. From Matomo 5.5.0-b2, optional config-ID randomization can create a new Visit for every tracking request, trading continuity and accuracy for less linkage. [Config ID FAQ](https://matomo.org/faq/general/how-is-the-visitor-config_id-processed/) [Config-ID randomization FAQ](https://matomo.org/faq/how-to/how-to-randomise-the-visitor-config_id-for-privacy/)

## Retention, Anonymization, and Deletion

- Matomo distinguishes raw Visit/action data from aggregated report data. On-Premise can retain both indefinitely; Cloud raw-data retention is plan-limited while report data can be unlimited. Matomo recommends purpose-based limits and suggests keeping detailed logs for 3-6 months in its privacy configuration guide; another retention guide cites 25 months as a CNIL-exemption ceiling and 24 months as a Cloud Business starting point. These are guidance/configuration facts, not a universal Matomo policy. [Data retention FAQ](https://matomo.org/faq/general/configure-data-retention/) [Privacy settings](https://matomo.org/docs/privacy-how-to/)
- Automatic raw-log purging permanently deletes visit/action/conversion log data but does not delete archived report data. The current source purger covers `log_visit`, `log_link_visit_action`, `log_conversion`, `log_conversion_item`, and unused `log_action` rows. [Historical deletion FAQ](https://matomo.org/faq/troubleshooting/faq_42/) [LogDataPurger.php, `5.x-dev`](https://raw.githubusercontent.com/matomo-org/matomo/5.x-dev/plugins/PrivacyManager/LogDataPurger.php)
- Specific-visit deletion is separate from retention purging. Matomo's GDPR tools find matching Visits, delete selected Visits, and reprocess affected historical reports; this requires raw Visit details still to exist. **Inference:** a Cimi account erasure flow must enumerate every matching site/Visit and coordinate report invalidation; Matomo does not expose this as a single durable "delete user" primitive. [Specific-visit deletion](https://matomo.org/faq/how-do-i-delete-rows-of-a-report-and-specific-visits-to-clean-up-some-of-the-reporting-data/) [Privacy Manager API source](https://raw.githubusercontent.com/matomo-org/matomo/5.x-dev/plugins/PrivacyManager/API.php)
- The current Privacy Manager API accepts data-subject descriptors containing `idsite` and `idvisit`; its finder returns at most 401 matching Visits. This makes pagination, completeness checks, and deletion auditability Cimi concerns. [Privacy Manager API source](https://raw.githubusercontent.com/matomo-org/matomo/5.x-dev/plugins/PrivacyManager/API.php)
- Historical anonymization is irreversible and can target a site/date range and selected Visit/action columns. User IDs are pseudonymized, not anonymized; clearing or pseudonymizing raw logs does not automatically invalidate old reports that may still contain personal data. [Past-data anonymization](https://matomo.org/faq/how-to/faq_35661/) [Report invalidation](https://matomo.org/faq/how-to/faq_155/)
- Matomo's GDPR developer contract is Visit-oriented: data stored in standard log tables is covered by built-in export/deletion/retention behavior, while plugins using custom tables must implement data-subject export, deletion, and old-log deletion hooks. [GDPR plugin guide](https://developer.matomo.org/guides/gdpr)

## Implications and Questions for Cimi

- Should Cimi's anonymous identity be a Matomo Visitor ID, accepting browser/domain scope and consent implications, or a Cimi-owned opaque identifier with explicit lifecycle and deletion semantics?
- Is a Matomo Visit an analytics session only, or is Cimi tempted to use it as an application session? The 30-minute timeout, midnight, campaign, logout, and device rules argue for keeping the models separate.
- If cross-device anonymous linking is needed before login, what authenticated, short-lived handoff mechanism will protect the Visitor ID and how will Cimi revoke or erase that link?
- At login, will Cimi send a stable opaque account ID as `uid` on every applicable hit, and will it keep the raw account ID out of Matomo by enabling User-ID pseudonymization? A salted pseudonym still needs a lawful basis and deletion plan.
- On logout, should Cimi prioritize continuity or privacy? The privacy-preserving choice is `resetUserId()` plus a forced new Visit, followed by verification that no post-logout hit carries `uid`.
- Which traits are truly visit/action facts versus durable account attributes? Matomo Custom Dimensions are suitable for minimized analytics context; durable profile traits should remain in Cimi and be sent only when necessary.
- What are the exact retention targets for raw logs, reports, browser identifiers, consent state, backups, and Matomo plugin tables? Matomo's raw-log purge and specific-Visit deletion do not automatically cover Cimi's surrounding systems.
- Which pinned Matomo release and configuration will Cimi support, especially for `setVisitorId()` persistence and `enable_userid_overwrites_visitorid`? Add tests for cookie loss, consent denial/revocation, login/logout, two devices, deletion, anonymization, and report reprocessing.
