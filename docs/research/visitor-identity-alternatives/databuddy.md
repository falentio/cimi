# Databuddy Analytics: Visitor Identity Research

Research for [Cimi issue #5](https://github.com/falentio/cimi/issues/5). Sources were checked on **2026-08-22**. The implementation references below use Databuddy's `main` snapshot at commit [`d15fcb5`](https://github.com/databuddy-analytics/Databuddy/commit/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3), committed 2026-08-21; its package metadata reports `@databuddy/sdk` **2.6.0** ([source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/sdk/package.json)).

## Bottom Line

Databuddy is **cookieless, but not identifier-free in the current SDK**. The browser creates a persistent `anon_*` identifier in `localStorage`, a temporary `sess_*` identifier in `sessionStorage`, and can persist an identified profile ID plus traits. The current tracker sends these identifiers to Databuddy; the server stores an identifier directly or as a daily-salted hash depending on configuration ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts), [event-service source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/lib/event-service.ts), [privacy transform source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/lib/security.ts)).

There is a material documentation conflict. The current SDK documentation documents `identify()`, persistent profiles, and cross-domain ID propagation ([identify docs](https://www.databuddy.cc/docs/sdk/identify-users), [tracker docs](https://www.databuddy.cc/docs/sdk/tracker)). Databuddy's older Data Policy, last updated **2024-12-22**, describes a daily-salted anonymous signature and says individual visitors cannot be identified ([Data Policy](https://www.databuddy.cc/data-policy)). The hosted Privacy Policy, last updated **2025-06-03**, likewise says Databuddy does not identify users across sessions and has no user profiles ([Privacy Policy](https://www.databuddy.cc/privacy)). Cimi should not treat the older privacy claims as the current technical contract without clarification or version pinning.

## Identity And Sessions

| Concept | Documented/current behavior | Persistence and linkage |
| --- | --- | --- |
| Anonymous visitor/device ID | A UUID-shaped `anon_*` ID is created with a secure random UUID helper and stored under `localStorage["did"]`; an `anonId` URL parameter takes precedence and overwrites local storage ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts)). The SDK docs describe it as an anonymous device ID persistent across sessions ([tracker docs](https://www.databuddy.cc/docs/sdk/tracker)). | It survives reloads and browser sessions until local storage is cleared, `clear()` is called, or opt-out cleanup runs. Current event construction includes `anonymousId`; the default server path daily-salts it before storage, while `anonymizeVisitorIds: false` preserves the supplied value ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts), [security source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/lib/security.ts)). |
| Session ID | A `sess_*` ID is stored under `sessionStorage["did_session"]`; the SDK documents a new session after 30 minutes of inactivity ([tracker docs](https://www.databuddy.cc/docs/sdk/tracker)). The source stores a timestamp and accepts the existing ID only while its age is below 30 minutes ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts)). | It survives reloads in the same browser tab and is cleared with session storage on tab/window close according to Databuddy's security docs ([security docs](https://www.databuddy.cc/docs/security)). A `sessionId` URL parameter can seed/continue it across domains ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts)). The source checks inactivity at tracker initialization and BFCache restoration; it does not show an idle timer that rotates the ID while a page remains open. This last sentence is an implementation observation, not a Databuddy product promise.
| Identified profile | `identify(profileId, traits?)` stores the profile ID under `localStorage["did_profile"]`, sends an `/identify` request with the anonymous ID, and attaches `profileId` to later events. The documented maximum is 128 characters; Databuddy recommends an opaque stable application ID, not an email address ([identify docs](https://www.databuddy.cc/docs/sdk/identify-users), [tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts)). | The profile ID persists across reloads and sessions. The backend stores a website-scoped profile, a website-scoped `anonymousId -> profileId` alias, and trait history ([identify route](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/routes/identify.ts), [identity service](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/services/src/identity.ts), [identity schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/drizzle/schema/identity.ts)). The docs claim that the same profile ID collapses activity across devices; the source supports this only when the application sends the same profile ID and performs the corresponding identify calls ([identify docs](https://www.databuddy.cc/docs/sdk/identify-users)). |
| Traits | Traits are scalar strings, numbers, booleans, or `null`; the docs specify 50 keys and a 2 KB serialized limit. `null` removes a trait ([identify docs](https://www.databuddy.cc/docs/sdk/identify-users)). | `email` and display names are specially handled; the source encrypts them when `DATABUDDY_ENCRYPTION_KEY` is configured and keeps a deterministic email lookup hash. Other traits and trait-change history are stored in PostgreSQL ([identity service](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/services/src/identity.ts), [identity schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/drizzle/schema/identity.ts)). |

## Storage And Linking

- Databuddy states that it sets no tracking cookies and uses local/session storage for IDs ([security docs](https://www.databuddy.cc/docs/security), [vanilla JS docs](https://www.databuddy.cc/docs/sdk/vanilla-js)). The current HTTP client also sends analytics with `credentials: "omit"` ([client source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/client.ts)). “No cookies” therefore does **not** mean “no browser persistence.”
- Cross-domain continuity is explicitly supported by copying `anonId` and `sessionId` into URL parameters; the destination tracker reads them and stores them locally ([tracker docs](https://www.databuddy.cc/docs/sdk/tracker), [tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3)). **Inference:** URL parameters can expose these IDs to browser history, server logs, or referrer processing unless the integrating application removes or contains them; Databuddy's cited docs do not specify a mitigation.
- The current source contradicts the Security page's example statement that the anonymous ID is “never sent to servers”: the tracker includes it in event payloads, and the backend's `buildTrackEvent()` writes the processed value to the `anonymous_id` column ([security docs](https://www.databuddy.cc/docs/security), [tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts), [event service](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/lib/event-service.ts)).
- `clearProfile()` removes only the browser's `did_profile` state and keeps the anonymous ID; subsequent activity is anonymous in the SDK ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3)). The source does not make a deletion request when `clearProfile()` runs. **Inference:** logout/unlink is not equivalent to deleting the already-stored profile, alias, traits, or historical events.
- `clear()` discards queued events, removes local anonymous/session/profile state, and generates fresh in-memory IDs; it likewise does not call a server-side deletion endpoint ([tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3)).

## Privacy, Consent, And PII

- Databuddy's documentation claims anonymous analytics can use legitimate interest without a consent banner ([security docs](https://www.databuddy.cc/docs/security), [GDPR guide, last updated December 2024](https://www.databuddy.cc/docs/compliance/gdpr-compliance-guide)). This is Databuddy's documented position, not an independent legal conclusion.
- Databuddy's DPA places controller responsibility on the customer to establish a legal basis and says this may require visitor consent depending on the situation ([DPA, last updated 2024-12-22](https://www.databuddy.cc/dpa)). More importantly for Cimi, the current `identify()` docs explicitly say identification processes personal data and recommend a lawful basis, “typically consent,” plus a privacy-policy disclosure ([identify docs](https://www.databuddy.cc/docs/sdk/identify-users)).
- Current source honors Global Privacy Control, Do Not Track, and local opt-out flags. Opt-out cancels pending delivery, clears the anonymous/session/profile and attribution keys, and prevents network requests; opt-in removes the flags and reinitializes tracking ([privacy helpers](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/utils.ts), [tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/index.ts), [privacy tests](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/tests/privacy.spec.ts)). The opt-out preference itself is stored in local storage and persists across sessions ([vanilla JS docs](https://www.databuddy.cc/docs/sdk/vanilla-js)).
- The default server privacy transform uses a daily salt, so the same supplied anonymous ID produces a different stored hash on different days; `anonymizeVisitorIds: "auto"` keeps raw IDs only for an allowlist currently containing the United States, while `false` disables hashing ([security source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/lib/security.ts)). **Inference:** a default salted ID limits long-term joinability but does not make the browser ID or identified profile anonymous, especially when `identify()` and traits are used.
- Raw IP addresses are used for geolocation and converted to a short salted hash for the event row; the source requires a production `IP_HASH_SALT` ([IP/geo source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/utils/ip-geo.ts), [event service](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3)).
- Databuddy's event API and tracker docs advise not putting PII in event properties ([event API docs](https://www.databuddy.cc/docs/api/events), [tracker docs](https://www.databuddy.cc/docs/sdk/tracker)). That advice does not remove the separate PII path intentionally enabled by `identify()` traits.

## Retention And Deletion

- The Data Policy says most analytics data is retained **indefinitely while the account is active**; performance metrics are automatically deleted after **one year**. It says project or account deletion removes analytics data ([Data Policy, last updated 2024-12-22](https://www.databuddy.cc/data-policy)).
- The DPA says data is retained while the account or project exists; deleting the account or project deletes associated anonymous analytics and personal information. It allows some data to remain in backups temporarily, inaccessible for processing, and says Databuddy will confirm deletion in writing ([DPA, last updated 2024-12-22](https://www.databuddy.cc/dpa)).
- The Privacy Policy says an end user cannot have specific analytics data deleted because Databuddy says it cannot identify that end user; it instead refers to automatic deletion under retention policies ([Privacy Policy, last updated 2025-06-03](https://www.databuddy.cc/privacy)). No end-user deletion period is stated there.
- The current ClickHouse schemas contain monthly/date partitions but no `TTL` clause for events or custom events ([events schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/clickhouse/schema/analytics/core/events.sql), [custom events schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/clickhouse/schema/analytics/core/custom_events.sql)). **Inference:** the repository does not itself establish the policy's indefinite/one-year purge behavior; an external job or operational policy may exist, but it was not found in the reviewed source.
- The reviewed current materials do not document a visitor-level deletion API, an anonymous-ID erasure workflow, or a profile-retention period. The profile router exposes reads and trait history, while `clearProfile()` is client-local ([profile router](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/rpc/src/routers/profiles.ts), [tracker source](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/tracker/src/core/tracker.ts)). **Unavailable:** whether Databuddy support can fulfill a visitor-specific request by other means.
- Website deletion cascades PostgreSQL profiles, aliases, and profile-trait history through foreign keys ([identity schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/drizzle/schema/identity.ts)). The website service's deletion path deletes the website row, but the ClickHouse event tables are independent ([website service](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/services/src/websites.ts), [events schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/clickhouse/schema/analytics/core/events.sql)). **Inference:** the source inspected does not prove that website deletion removes historical ClickHouse events; this must be confirmed before relying on the DPA's deletion promise.

## Implications And Questions For Cimi

- Should Cimi model Databuddy's default `anon_*` value as a site/browser pseudonymous visitor identifier, not as a truly anonymous visitor, given local persistence and server receipt?
- Is a 30-minute inactivity timeout sufficient, and should session rotation be timer-driven rather than checked only at initialization/BFCache restore?
- Does Cimi want optional identified profiles at all? If yes, define consent, allowed profile IDs/traits, unlink semantics, and whether prior anonymous events become attributable. Databuddy's docs claim earlier same-session pageviews are attached, while the visible ingestion path writes `profile_id` on events and separately stores aliases; this historical backfill behavior is not established by the reviewed source ([identify docs](https://www.databuddy.cc/docs/sdk/identify-users), [identify route](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/apps/basket/src/routes/identify.ts), [events schema](https://github.com/databuddy-analytics/Databuddy/blob/d15fcb5dac3605746dd08a35aac3de5f3ab4c2f3/packages/db/src/clickhouse/schema/analytics/core/events.sql)).
- What is Cimi's explicit retention for raw events, sessions, visitor IDs, profile aliases, traits, trait history, derived aggregates, backups, and deletion tombstones? Databuddy supplies account/project-level statements, but not a visitor-level schedule.
- Must opt-out stop future collection only, or also trigger server-side erasure? Databuddy's current opt-out clears browser state and pending delivery but does not document server deletion.
- Will cross-domain continuity be permitted? If so, how will Cimi avoid putting identity values in URLs, history, logs, or referrers?
- If using Databuddy as an alternative, which contract is authoritative: the current SDK/source behavior or the older “no identification/no profiles” privacy language? Pin the SDK/tracker version and obtain clarification before using Databuddy's privacy claims as Cimi requirements.
