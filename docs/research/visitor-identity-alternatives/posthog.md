# PostHog: Visitor Identity and Privacy Model

Research for [Cimi issue #5](https://github.com/falentio/cimi/issues/5),
"Define Cimi's visitor identity and privacy model".

- Investigated: 2026-08-22
- Source scope: official PostHog documentation, pricing, privacy policy, and
  `posthog-js` source
- Purpose: document PostHog's behavior; the Cimi recommendations below are
  inferences, not PostHog guarantees

## Executive Summary

PostHog has two primary client-side identity dimensions:

- `distinct_id` groups events into an identity. The SDK generates an anonymous
  value, and `identify()` can link it to an application-owned identifier. ([identifying users](https://posthog.com/docs/product-analytics/identify))
- `$session_id` groups events into a browser/device session. The default session
  ends after 30 minutes without activity or after 24 hours. ([sessions](https://posthog.com/docs/data/sessions))

PostHog does not make its anonymous `distinct_id` equivalent to an anonymous
person profile. Anonymous events can exist without a person profile; an
identified event creates or updates a person profile. A persistent `distinct_id`
can itself be personal data, so "anonymous" is an analytics state rather than a
privacy classification. ([people](https://posthog.com/docs/data/persons), [data collection](https://posthog.com/docs/privacy/data-collection))

For Cimi, PostHog should be treated as an analytics projection rather than the
authority for Visitor, Session, User, Trait, consent, or deletion state. Cimi
should define those concepts and pass PostHog only the identifiers and
properties allowed by Cimi policy.

## Concept Mapping

| Cimi concept | PostHog representation | Persistence and lifecycle | Important limitation |
| --- | --- | --- | --- |
| Visitor | No separate first-class visitor entity. Usually represented by the browser's anonymous `distinct_id`. | With default web persistence, the ID is stored in a cookie and `localStorage`; the default cookie expires after 365 days. The docs do not define a matching expiry for `localStorage`. ([persistence](https://posthog.com/docs/libraries/js/persistence)) | It is a vendor-generated browser identity, not necessarily a Cimi visitor record and not necessarily anonymous for privacy purposes. |

([people](https://posthog.com/docs/data/persons)) |

## Identity Lifecycle

### Anonymous start

The web SDK automatically assigns an anonymous ID and can capture events before
the application knows who the visitor is. With cookie or `localStorage`
persistence, the SDK can recognize that browser on later sessions. ([identify
users](https://posthog.com/docs/getting-started/identify-users), [persistence](https://posthog.com/docs/libraries/js/persistence))

The anonymous ID is not the same as a person profile. Anonymous events are
recorded without creating a profile; a profile is created after `identify()`, a
person-property call, or an event carrying `$set` or `$set_once`. ([people](https://posthog.com/docs/data/persons))

### Login or signup

Calling `identify(canonical_id, properties)` links the existing anonymous ID to
the supplied ID. PostHog says that past events from the anonymous ID and future
events from the identified ID are then associated with the identified user.
([identifying users](https://posthog.com/docs/product-analytics/identify))

The canonical ID must be stable and unique. If two real users are assigned the
same ID, PostHog treats them as one user. PostHog specifically warns against
generic or invalid IDs such as `null`, `true`, or a shared placeholder. ([identify
users](https://posthog.com/docs/getting-started/identify-users))

### Backend events

Backend SDKs do not have an anonymous browser session. Cimi must pass the same
`distinct_id` used by the frontend when it wants backend events to belong to the
same person. The frontend `$session_id` can also be passed explicitly when a
backend event belongs to that browser session. ([identifying users](https://posthog.com/docs/product-analytics/identify), [sessions](https://posthog.com/docs/data/sessions))

### Logout

PostHog recommends calling `reset()` on frontend logout so future events on a
shared device are not attributed to the previous user. `reset(true)` can also
reset the device ID. `reset()` starts a new session and session replay. ([identify
users](https://posthog.com/docs/getting-started/identify-users), [sessions](https://posthog.com/docs/data/sessions))

Resetting is an attribution boundary, not deletion. It does not remove already
stored events or person data.

### Linking additional IDs

`alias()` can connect another distinct ID to an existing user and merge past and
future events. PostHog documents two relevant restrictions: an alias ID cannot
already be associated with more than one distinct ID, and it cannot have
previously been used as the `distinct_id` argument to `identify()` or
`alias()`. ([identifying users](https://posthog.com/docs/product-analytics/identify))

If two already-identified profiles need to be merged, PostHog warns that the
dangerous merge operation is irreversible and should not replace a sound
identity design. ([identifying users](https://posthog.com/docs/product-analytics/identify))

## Persistence and Retention

### Browser persistence

The default web persistence mode is `localStorage+cookie`. The stored values
include the `distinct_id`, session ID, device ID, feature flags, super
properties, and some PostHog configuration. The default cookie is named from
the project key and expires after 365 days. ([persistence](https://posthog.com/docs/libraries/js/persistence))

Supported persistence modes are `localStorage+cookie`, `cookie`,
`localStorage`, `sessionStorage`, and `memory`. `memory` lasts only for the page
view. `disable_persistence: true` prevents browser storage, but the docs warn
that each refresh then looks like a new user unless the application calls
`identify()` on every load. ([persistence](https://posthog.com/docs/libraries/js/persistence))

The browser lifetime of an ID and the server retention lifetime of its events
are separate. A browser can present the same ID after older events have expired,
and a server-side deletion does not by itself remove the ID from the browser.
This separation is a Cimi design concern, not a PostHog-specific guarantee.

### Product analytics event retention

The current PostHog pricing page lists:

- Free: one project and one-year data retention
- Pay-as-you-go: six projects and seven-year data retention

These are plan-level product analytics retention values, not a guaranteed
per-identity lifetime and not a substitute for a Cimi retention policy. ([pricing](https://posthog.com/pricing))

### Session replay retention

Session replay has its own retention limits:

| Plan | Maximum recording retention |
| --- | --- |
| Free | 30 days |
| Pay-as-you-go | 90 days |
| Boost | 1 year |
| Scale | 1 year |
| Enterprise | 5 years |

Changing the replay retention setting affects new recordings only. Expiry or
manual deletion is not necessarily immediate. ([replay retention](https://posthog.com/docs/session-replay/recording-retention))

### Person profile retention

The documentation describes how person profiles are created, merged, and
deleted, but does not specify a separate person-profile expiry independent of
project retention. Cimi should therefore not assume that a person profile has a
shorter lifetime than its associated analytics data. ([people](https://posthog.com/docs/data/persons), [data storage](https://posthog.com/docs/privacy/data-storage))

## Consent and Privacy

### Opt out

`opt_out_capturing()` prevents all data from being captured and sent, including
autocapture, manual events, and session replay. The opt-out state is persisted
automatically in browser storage or cookies, with the persistence type
configurable. PostHog also supports opting out by default and opting in only
after consent. ([data collection](https://posthog.com/docs/privacy/data-collection))

PostHog recommends loading the SDK and controlling capture through consent
APIs rather than conditionally loading the SDK after a banner decision. This
allows the SDK to handle later consent changes consistently. ([data collection](https://posthog.com/docs/privacy/data-collection))

### Cookieless modes

PostHog supports `cookieless_mode: "always"` and `cookieless_mode: "on_reject"`:

- `always` does not store PostHog data in cookies, `localStorage`, or
  `sessionStorage`, and counts users using a server-calculated privacy-
  preserving hash.
- `on_reject` avoids browser storage until consent is granted. If consent is
  denied, PostHog can still count users with the privacy-preserving server hash.
- In `always` mode, PostHog warns that a persistent `distinct_id` is personal
  data and recommends avoiding identification. It documents
  `person_profiles: "never"` for making `identify()` calls no-ops and says
  `alias()` is not supported in this mode.

Cookieless tracking does not independently solve data collection or storage
compliance; those controls still need to be configured. ([data collection](https://posthog.com/docs/privacy/data-collection))

### Data minimization and processing

PostHog supports disabling client IP capture, masking or filtering captured
values, hashing PII before storage, dropping events, and IP anonymization.
PostHog's documentation makes the application responsible for deciding what
data to collect and whether that collection is lawful. ([data collection](https://posthog.com/docs/privacy/data-collection), [data storage](https://posthog.com/docs/privacy/data-storage), [privacy](https://posthog.com/docs/privacy))

The PostHog privacy policy says its hosted services collect technical data such
as IP address, device information, and pages or content viewed, and describes
the use of cookies and related technologies. It also states that PostHog does
not use third-party cookies. ([privacy policy](https://posthog.com/privacy))

## Deletion Semantics

Deleting a person is distinct from resetting a browser identity:

1. Person deletion is processed asynchronously. PostHog recommends not reusing
   the deleted `distinct_id` while deletion is pending.
2. The API can request deletion of the person's events with
   `delete_events=true`.
3. The API can request deletion of associated recordings with
   `delete_recordings=true`.
4. Event deletion is queued for background processing, including non-peak
   processing for the expensive ClickHouse deletion operation.
5. Recording deletion uses crypto-shredding when requested, making recordings
   unrecoverable.
6. PostHog provides a deletion-status endpoint for queued event deletion.

([people](https://posthog.com/docs/data/persons), [data storage](https://posthog.com/docs/privacy/data-storage), [Persons API](https://posthog.com/docs/api/persons))

Once deletion is fully processed, PostHog says it retains no data associated
with the deleted `distinct_id`. If reuse is unavoidable, PostHog documents a
Reset deleted person operation rather than silently reusing the value. ([data
storage](https://posthog.com/docs/privacy/data-storage))

## Cimi Implications

These are recommendations for Cimi, inferred from the behavior above:

- Keep Cimi's Visitor ID and User ID authoritative in Cimi. Treat PostHog's
  `distinct_id` as an adapter-level identifier.
- Model anonymous-to-authenticated linking as an explicit state transition;
  call `identify()` only with a stable Cimi user ID.
- Call `reset()` at every frontend logout boundary, including shared-device
  scenarios.
- Keep consent state in Cimi or its consent system and configure PostHog to be
  opted out by default when consent is required.
- Use a trait allowlist. Email, names, account IDs, URLs, and free-form
  properties should not be forwarded by default merely because PostHog accepts
  them.
- Track vendor deletion as a state machine such as `requested`, `queued`, and
  `completed`; a local deletion request must not be reported as complete merely
  because `reset()` removed the browser linkage.
- Keep event retention and session replay retention as separate policy values.
  A replay may have a shorter or different lifetime than the event stream.
- Do not reuse a deleted vendor identity until the vendor deletion workflow is
  complete, or use a new vendor identity for the new Cimi user.
- If Cimi needs identity across analytics domains, define the join boundary
  explicitly. Do not assume that sharing a browser cookie or a raw email is
  acceptable cross-domain identity linking.

## Open Decisions for Cimi

1. Is Cimi's Visitor ID first-party and Cimi-owned, or may an analytics SDK
   generate it?
2. What is the allowed anonymous identity lifetime in the browser, and does it
   differ by consent state?
3. Should Cimi count consent-denied visitors with a privacy-preserving aggregate,
   or capture nothing at all?
4. What are the maximum event, person, and session replay retention periods for
   each environment?
5. Does deleting a Cimi user require deleting anonymous pre-login activity that
   has been linked to that user?
6. Which traits are permitted in analytics, and which must be redacted before
   ingestion?
7. Which analytics domains may share an identity, and what explicit event or
   consent permits that join?
