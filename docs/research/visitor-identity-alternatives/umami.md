# Umami visitor identity and privacy research

**For:** Cimi issue [#5](https://github.com/falentio/cimi/issues/5)
**Research context:** Official Umami documentation was checked on 2026-08-22. The documentation says it covers Umami v3; the current official source release at that date is [`v3.3.1`](https://github.com/umami-software/umami/releases/tag/v3.3.1), published 2026-08-20. Umami v3.3.0 introduced session identity stitching and relational session deletion. ([release notes](https://github.com/umami-software/umami/releases/tag/v3.3.0))

Only Umami-owned documentation, source repository files, release notes, and Umami's privacy policy are cited below.

## Executive findings

- **Documented:** Default Umami tracking uses no tracking cookies, does not track across sites, and presents visitors as anonymous. ([FAQ](https://docs.umami.is/docs/faq), [introduction](https://docs.umami.is/docs))
- **Documented:** In v3.3.1, an anonymous session ID is deterministically derived server-side from the tracked source, client IP, user agent, and a rotating salt. The default salt rotation is monthly. The IP is used for location/session calculation but is not stored in the analytics data. ([`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts), [`crypto.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/lib/crypto.ts), [metric definitions](https://docs.umami.is/docs/metric-definitions))
- **Documented:** `umami.identify()` is an explicit integrator-controlled path that sends a Distinct ID and optional session data to Umami. Since v3.3, identified sessions are linked into a combined profile without merging the underlying sessions. ([tracker functions](https://docs.umami.is/docs/tracker-functions), [Distinct IDs](https://docs.umami.is/docs/distinct-ids), [`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts))
- **Documented:** Self-hosted analytics are retained indefinitely unless manually deleted. Cloud documentation gives no analytics retention period; Cloud account deletion is documented as permanently removing account data, websites, teams, and analytics history. ([self-hosted FAQ](https://docs.umami.is/docs/faq), [Cloud FAQ](https://docs.umami.is/docs/cloud/faq), [delete account](https://docs.umami.is/docs/cloud/delete-account))
- **Inference:** Umami's default anonymous identity is a pseudonymous, server-derived session bucket, not a durable browser visitor ID. The v3.3.1 tracker has no persistent anonymous ID and keeps its cache and current identity only in JavaScript memory. ([tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts))

## Canonical concepts

| Cimi concept | Umami v3 behavior | Evidence and interpretation |
| --- | --- | --- |
| **Visitor / anonymous identity** | Umami's `Visitors` metric is the unique number of sessions. A session is calculated from request/browser attributes and a rotating salt; it is not a separate durable visitor record. | **Documented:** [metric definitions](https://docs.umami.is/docs/metric-definitions). **Inference:** Treat this as a pseudonymous session identity with a rotation boundary, not as a permanent anonymous user. |
| **Session** | The server stores a UUID-like Session ID. In v3.3.1, the relational server computes it as `uuid(sourceId, ip, userAgent, sessionSalt)`; the default `sessionSalt` is monthly. | **Documented:** [`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts), [`crypto.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/lib/crypto.ts). The public docs describe the same concept as a hash of IP, user agent, and website ID. ([Sessions](https://docs.umami.is/docs/sessions)) |
| **Visit** | A visit is a finer-grained unit within a session. The server derives a visit ID using the session ID and an hourly salt; without an overridden timestamp, the cached visit expires after 30 minutes of inactivity. | **Documented:** [metric definitions](https://docs.umami.is/docs/metric-definitions), [`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts). |
| **Identified user / Distinct ID** | The integrator supplies an ID through `umami.identify()` or an event/API payload. The ID is limited to 50 characters. It may be an internal ID, email, or hash, although Umami recommends internal IDs or hashes instead of email. | **Documented:** [Distinct IDs](https://docs.umami.is/docs/distinct-ids), [identify logged-in users](https://docs.umami.is/docs/guides/identify-logged-in-users). **Cimi implication:** The value is caller-controlled and can be personal data. |
| **Linked identity** | `identify` creates a website-scoped `session_link` between the current Session ID and the supplied Distinct ID, and updates the session's Distinct ID. Other sessions with that same Distinct ID are shown in one profile. | **Documented:** [`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts), [`saveSessionLink.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/queries/sql/sessions/saveSessionLink.ts), [migration](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/prisma/migrations/21_add_session_link/migration.sql), [Distinct IDs](https://docs.umami.is/docs/distinct-ids). **Important:** Sessions remain separate; linking is not a merge. |
| **Traits / session properties** | Umami calls these “Session Data.” `identify(data)` stores flattened JSON properties for the current session. Relational storage enforces one value per `(session_id, data_key)` and updates an existing key. | **Documented:** [tracker functions](https://docs.umami.is/docs/tracker-functions), [`saveSessionData.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/queries/sql/sessions/saveSessionData.ts), [schema](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/prisma/schema.prisma). |

## Persistence and storage

- **Documented:** The official FAQ says the tracking code does not use cookies. The identify guide says session data is stored server-side and that users who are not logged in remain anonymous. ([FAQ](https://docs.umami.is/docs/faq), [identify guide](https://docs.umami.is/docs/guides/identify-logged-in-users))
- **Documented:** The v3.3.1 tracker uses `localStorage` only to check `umami.disabled`; it does not write an anonymous visitor ID, Distinct ID, or session token there. The response cache, current identity, and tracker state are JavaScript variables. ([tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts), [exclude own visits](https://docs.umami.is/docs/exclude-my-own-visits))
- **Inference:** A full page reload loses the browser-side `identity` and in-memory cache. Anonymous continuity can still recur within the salt period when the server sees the same source, IP, and user agent, but it is not browser-persisted and is sensitive to those inputs changing. ([tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts), [`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts))
- **Documented:** The opt-out setting is a per-website local-storage flag: `localStorage.setItem('umami.disabled', 1)` stops tracking and removing the key resumes it. ([exclude own visits](https://docs.umami.is/docs/exclude-my-own-visits), [tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts))
- **Documented:** Cross-device continuity requires the integrator to send the same Distinct ID; Umami does not merge the device/browser sessions themselves. The `session_link` key includes `website_id`, so the source-level linkage is website-scoped. ([Distinct IDs](https://docs.umami.is/docs/distinct-ids), [schema](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/prisma/schema.prisma))

## Privacy and consent

- **Documented:** Umami describes the default product as cookie-free, non-cross-site, and anonymized. The documented analytics fields include page/referrer data, browser, OS, device, screen, language, and location; the IP used to derive location is stated to be never stored in analytics. ([introduction](https://docs.umami.is/docs), [FAQ](https://docs.umami.is/docs/faq), [metric definitions](https://docs.umami.is/docs/metric-definitions))
- **Documented:** The tracker is automatic by default. Integrators can disable initialization with `data-auto-track="false"`, respect Do Not Track with `data-do-not-track="true"`, or inspect/modify/cancel a payload with `data-before-send`. ([tracker configuration](https://docs.umami.is/docs/tracker-configuration), [tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts))
- **Documented:** The FAQ answers that no cookie notice is needed because the tracking code uses no cookies. This is Umami's product documentation, not a Cimi-specific legal determination. ([FAQ](https://docs.umami.is/docs/faq))
- **Inference:** The reviewed tracker documentation/source exposes no consent state, consent log, category-based gate, or visitor-facing withdrawal API. Cimi would need to gate tracker loading/sending itself if its policy requires prior consent, and should define what happens when consent is withdrawn. ([tracker configuration](https://docs.umami.is/docs/tracker-configuration), [tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts))
- **Documented:** `identify()` accepts arbitrary session data and Umami's examples include names, email addresses, plans, and companies. The official guide recommends internal IDs rather than email and suggests hashing email when correlation is needed without storing the email. ([tracker functions](https://docs.umami.is/docs/tracker-functions), [identify guide](https://docs.umami.is/docs/guides/identify-logged-in-users))
- **Inference:** “No personal data” is safe only for Cimi's constrained anonymous configuration; using `identify`, session properties, or custom event data changes the data-protection analysis. Cimi should treat identifiers and traits as potentially personal data even though the default tracker is cookie-free. ([tracker functions](https://docs.umami.is/docs/tracker-functions), [identify guide](https://docs.umami.is/docs/guides/identify-logged-in-users))

## Retention and deletion

### Retention

- **Documented:** Self-hosted data is retained indefinitely unless the operator manually deletes it. Monthly salt rotation changes the anonymous session calculation; it is not documented as a deletion or purge mechanism. ([FAQ](https://docs.umami.is/docs/faq), [metric definitions](https://docs.umami.is/docs/metric-definitions), [`crypto.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/lib/crypto.ts))
- **Documented gap:** The current Cloud FAQ explains usage measurement, regions, compliance, and export, but does not state an analytics retention duration. ([Cloud FAQ](https://docs.umami.is/docs/cloud/faq))
- **Documented, Cloud service scope:** Umami's privacy policy says personal information is kept as long as necessary, then deleted or anonymized where possible, with backups potentially isolated until deletion; it also describes rights including erasure and consent withdrawal. This policy governs Umami's own Services and should not be assumed to define retention for a Cimi self-hosted deployment. ([Umami privacy policy](https://umami.is/privacy))

### Deletion

- **Documented:** In v3.3.1, `DELETE /api/websites/:websiteId/sessions/:sessionId` is available only with relational storage and requires website deletion permission. It deletes the selected session's event data, saved replays, replay chunks, heatmap events, revenue, session data, session links, website events, and session row in one transaction. ([session API route](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/websites/%5BwebsiteId%5D/sessions/%5BsessionId%5D/route.ts), [`deleteSession`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/queries/prisma/session.ts))
- **Inference:** Deleting one session does not delete other sessions linked to the same Distinct ID: the delete path receives one `sessionId`, while profile expansion separately queries all linked IDs/sessions. A “delete this identified person” workflow therefore needs to enumerate and delete every relevant linked session and associated data, or use a broader website reset. ([session API route](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/websites/%5BwebsiteId%5D/sessions/%5BsessionId%5D/route.ts), [`getLinkedSessionIds.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/queries/sql/sessions/getLinkedSessionIds.ts))
- **Documented:** Website reset removes the website's analytics-dependent data and records a reset timestamp; website deletion removes dependent analytics data and then hard-deletes the website for self-hosted mode or soft-deletes the website in Cloud mode. ([`website.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/queries/prisma/website.ts), [website data UI](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/%28main%29/websites/%5BwebsiteId%5D/settings/WebsiteData.tsx))
- **Documented:** Cloud account deletion is permanent and removes all data, websites, teams, and analytics history; export is recommended first. ([delete account](https://docs.umami.is/docs/cloud/delete-account), [Cloud export](https://docs.umami.is/docs/cloud/export-data))
- **Inference:** The reviewed source has no anonymous visitor self-service deletion, deletion tombstone, or future-collection suppression keyed by a deleted identity. Cimi must decide whether deletion means only removing historical rows or also preventing the same person from being re-collected. ([tracker source](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/tracker/index.ts), [`route.ts`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/app/api/send/route.ts), [`deleteSession`](https://raw.githubusercontent.com/umami-software/umami/v3.3.1/src/queries/prisma/session.ts))

## Implications and questions for Cimi

1. Should Cimi's anonymous Visitor be a durable browser identity, or should it intentionally follow Umami's server-derived, salt-rotated session model?
2. Is `Distinct ID` allowed only after an explicit product consent/login boundary? If yes, which internal identifier and trait allowlist are safe, and how will logout or account reassignment be handled?
3. Does Cimi need continuity across reloads, devices, or domains? Umami provides cross-device linking only when Cimi supplies the same ID; its source linkage is website-scoped and the default tracker has no persistent anonymous ID.
4. What is the required retention period for anonymous sessions, identified sessions, traits, event data, replays, heatmaps, and revenue records? Self-hosted Umami has no automatic retention limit documented.
5. Does deletion target one session, all sessions linked to an identity, or every event/trait/replay attributable to a person? The built-in session delete is relational-only and one-session-at-a-time.
6. How will consent withdrawal and deletion suppress future collection, especially when a browser has no durable Umami identity but an application can call `identify()` again?
7. If Cimi uses Umami Cloud rather than self-hosting, what contractual retention/deletion SLA and export/deletion confirmation are required, given that the public Cloud FAQ does not state an analytics retention window?
