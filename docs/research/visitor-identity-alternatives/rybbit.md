# Rybbit Visitor Identity Research

Scope: Rybbit's visitor identity, sessions, identification, traits, alias/backfill behavior, persistence, consent/privacy, retention, and deletion semantics for Cimi issue #5.

Sources are limited to Rybbit's official documentation, official privacy/legal pages, and the official source repository in this workspace. The repository snapshot used here is `rybbit` at commit `64f8c4fb7f394bdfe9379717de8e6c21758b1ac2`.

## Findings

Rybbit has five distinct identity concepts, not one universal visitor key:

| Cimi concept | Rybbit behavior | Persistence and evidence |
| --- | --- | --- |
| Anonymous identity / visitor | The documented `user_id` is a hash of visitor IP plus browser user-agent. Current code hashes a bucketed IP and normalized user-agent with an optional daily site salt, then truncates the SHA-256 result to 12 characters. A supplied `anonymous_id` is also hashed with site ID and the optional salt. | Event rows store the resulting `user_id`; the source does not store the raw fingerprint inputs as the identity key. [`definitions.mdx`](https://rybbit.com/docs/definitions#user-id), `rybbit/server/src/services/userId/userIdService.ts:80-135`, `rybbit/server/src/services/tracker/utils.ts:124-156` |
| Session | A session ends after 30 minutes of inactivity. The implementation keeps the active session ID in Redis with a sliding 30-minute TTL; it is not a durable session table. | `rybbit/server/src/services/sessions/sessionsService.ts:6-10,29-49`; [`definitions.mdx`](https://rybbit.com/docs/definitions#sessions) |
| Identified user | `identify(userId, traits?)` attaches an application-provided custom ID. The ID is stored exactly as supplied, is limited to 255 characters, and is written to event `identified_user_id`. Users sharing an identified ID aggregate as one user across aliases/devices. | [`identify-users.mdx`](https://rybbit.com/docs/identify-users#windowrybbitidentifyuserid-traits), `rybbit/server/src/analytics-script/tracking.ts:435-455`, `rybbit/server/src/services/tracker/utils.ts:135-157`, `rybbit/server/src/db/clickhouse/schema/core.ts:115-125` |
| Trait / profile | Traits are JSON profile data. `identify` and `setTraits` merge fields; `null` removes a field. `username`, `name`, and `email` have display semantics. The limit is 2 KB per identify call. | [`identify-users.mdx`](https://rybbit.com/docs/identify-users#special-trait-fields), `rybbit/server/src/services/tracker/identifyService.ts:14-35,133-157`, `rybbit/server/src/db/postgres/schema.ts:543-558` |
| Alias / linked device | An alias maps one site-scoped anonymous ID to one identified user ID. The database enforces uniqueness for `(site_id, anonymous_id)`, while one identified user can have multiple aliases/devices. | `rybbit/server/src/db/postgres/schema.ts:561-577`; [`Get User Info`](https://rybbit.com/docs/api/users/info) documents `linked_devices` |

### Identity and session details

- For ordinary browser `/track` events, the canonical anonymous identity is derived server-side from the request IP and user-agent. The browser script's separate `namespace-visitor-id` is persisted in `localStorage` and sent to feature-flag evaluation, but it is not placed in the normal tracking payload. This is an important distinction between a client storage ID and Rybbit's analytics `user_id`. [`rybbit/server/src/analytics-script/config.ts:23-43,65-83`, `rybbit/server/src/analytics-script/tracking.ts:167-194`, `rybbit/server/src/services/tracker/utils.ts:124-156`]
- The optional `saltUserIds` setting changes the fingerprint daily. Rybbit documents this as forgetting unique users every day; the source derives the salt from the event's UTC day. With salting enabled, a visitor returning on a later day gets a new anonymous fingerprint unless an identified ID is used for aggregation. [`site-settings.mdx`](https://rybbit.com/docs/site-settings#user-id-salting), `rybbit/server/src/services/userId/userIdService.ts:38-67,109-126`
- Anonymous sessions use a Redis key containing site ID and anonymous `user_id`. Identified sessions use a hash of anonymous `user_id` plus custom `identified_user_id`; the custom ID is not exposed in the Redis key. Thus two identified users sharing a device fingerprint remain in separate sessions. `rybbit/server/src/services/sessions/sessionsService.ts:29-44`; [`identify-users.mdx`](https://rybbit.com/docs/identify-users#important-notes)
- Events retain both fields: `user_id` remains the device fingerprint and `identified_user_id` is the custom ID when present. The sessions and users API documents expose both fields and traits. [`sessions/list.mdx`](https://rybbit.com/docs/api/sessions/list#session-object), [`users/list.mdx`](https://rybbit.com/docs/api/users/list#user-object), `rybbit/server/src/services/tracker/pageviewQueue.ts:81-87`

## Identify, traits, aliases, and backfill

- The browser SDK's `identify` request contains `site_id`, `user_id`, `traits`, and `is_new_identify`; it does not contain `anonymous_id`. The server therefore resolves the browser's current IP and user-agent when it creates the alias. Explicit `anonymous_id` support exists in the ingestion/identify schemas and in the dashboard-side identify endpoint. [`rybbit/server/src/analytics-script/tracking.ts:472-491`, `rybbit/server/src/services/tracker/identifyService.ts:18-35,71-90`, `rybbit/server/src/services/tracker/trackingPayload.ts:4-20`, `rybbit/server/src/api/analytics/users/identifyUser.ts:11-25,34-46`]
- On a new browser alias, Rybbit creates a profile shell, inserts the alias, stores or merges traits, and queues asynchronous backfill. Existing aliases are not backfilled again; if the same device is identified as another user, the alias is repointed and future events use the new user, while already attributed events remain attributed to the prior user. [`identify-users.mdx`](https://rybbit.com/docs/identify-users#important-notes), `rybbit/server/src/services/tracker/identifyService.ts:92-157`
- Browser identify backfill is bounded to the most recent 30 days in the current source. It is queued in five-minute batches, updates `events`, `session_replay_events`, and `session_replay_metadata_v2`, only fills blank `identified_user_id` values, retries failures up to three attempts, and can leave rows anonymous after exhausted failures. `rybbit/server/src/services/tracker/identifyService.ts:38-56`, `rybbit/server/src/services/tracker/identityBackfillQueue.ts:16-39,85-93,141-195`
- The dashboard-side `POST /sites/:siteId/users/identify` deliberately requests a full-history backfill (`days: null`) because an operator asserts that the device history belongs to the identified user. It is a separate, authenticated route from the public browser `/api/identify` endpoint. `rybbit/server/src/api/analytics/users/identifyUser.ts:34-39,71-85`, `rybbit/server/src/index.ts:373-376`
- The official identify documentation says a new alias retroactively updates “all past anonymous events,” but it does not disclose the browser path's 30-day limit. The precise interpretation is therefore: full history for the dashboard action, recent history for ordinary browser identify in this source snapshot. This is a documentation/implementation mismatch, not an inference. [`identify-users.mdx`](https://rybbit.com/docs/identify-users#how-it-works), `rybbit/server/src/services/tracker/identifyService.ts:38-40`, `rybbit/server/src/api/analytics/users/identifyUser.ts:79-85`
- Cross-device linking is achieved by reusing the same custom `user_id` across separate site-scoped aliases; Rybbit does not merge anonymous fingerprints into one fingerprint. [`identify-users.mdx`](https://rybbit.com/docs/identify-users#important-notes), `rybbit/server/src/db/postgres/schema.ts:561-577`

## Persistence and retention

- Browser storage has no expiry in the tracker source. `namespace-visitor-id` persists the generated browser ID; `namespace-user-id` persists the custom identified ID until `clearUserId`, local-storage deletion, or browser storage removal. `clearUserId` removes only the local custom ID, resets session replay's current user ID, and refreshes feature flags. `rybbit/server/src/analytics-script/config.ts:23-43`, `rybbit/server/src/analytics-script/tracking.ts:435-455,497-510`; [`identify-users.mdx`](https://rybbit.com/docs/identify-users#windowrybbitclearuserid)
- Profiles and aliases are PostgreSQL rows with no TTL in the schema. They therefore behave as durable identity records until explicit user/site deletion; this persistence conclusion is an inference from the schema and deletion paths, not a separately documented retention promise. `rybbit/server/src/db/postgres/schema.ts:543-577`
- The main `events` table DDL in this snapshot has no ClickHouse `TTL` clause. Official privacy materials nevertheless state that self-hosted retention is administrator-configurable and Cloud retention is 3 years for Standard, 5 years for Pro, and indefinite for Enterprise. The repository path shown here does not establish how the Cloud plan policy is enforced, so Cimi should not assume that the local DDL alone is the Cloud retention contract. [`rybbit/server/src/db/clickhouse/schema/core.ts:83-134`](../../../rybbit/server/src/db/clickhouse/schema/core.ts), [`Privacy Policy`](https://rybbit.com/privacy#data-retention)
- Session replay tables have a 30-day TTL in the source. Bot audit tables have separate 3-month and 30-day TTLs. These are separate from the main event retention policy. `rybbit/server/src/db/clickhouse/schema/core.ts:141-239,241-263,276-312,337-395`
- The official retention documents are not internally uniform about termination timing: the DPA says Personal Data will be deleted or returned within 30 days after service termination, while the security page says cancellation data deletion occurs within 60 days. These are service-level statements, not visitor-level deletion semantics, and need one Cimi interpretation. [`DPA`](https://rybbit.com/dpa#10-data-retention), [`Security`](https://rybbit.com/security#data-deletion)

## Cookies, storage, privacy, and consent

- Rybbit's privacy policy and security page describe the default product as cookieless and say it uses no local storage for tracking. The official identify and web SDK documentation explicitly says custom IDs are stored in `localStorage`, and the source stores both a visitor ID and custom user ID there. The statements can only be reconciled by scoping “no local storage” to the anonymous default path; as written, the official materials contradict the identify path. [`Privacy Policy`](https://rybbit.com/privacy#gdpr-and-privacy-regulations-compliance), [`Security`](https://rybbit.com/security#visitor-privacy-protection), [`identify-users.mdx`](https://rybbit.com/docs/identify-users#windowrybbitidentifyuserid-traits), [`JavaScript SDK`](https://rybbit.com/docs/sdks/web#user-identification), `rybbit/server/src/analytics-script/config.ts:23-43`
- The default anonymous path is described as typically not requiring a consent banner because no cookies are used. Identification is explicitly treated differently: Rybbit's identify documentation calls for a lawful basis, usually consent, a privacy notice, access/deletion capability, and explicit consent for traits. [`Privacy Policy`](https://rybbit.com/privacy#no-cookies-policy), [`identify-users.mdx`](https://rybbit.com/docs/identify-users#gdpr--privacy-compliance)
- The source implements an opt-out, not a consent workflow. Before initialization it checks `window.__RYBBIT_OPTOUT__` or the persistent `disable-<namespace>` local-storage key and installs a no-op API. There is no consent state in the tracker API shown here, so consent gating is an application/Cimi responsibility. The last sentence is an inference from the source, not a Rybbit legal conclusion. `rybbit/server/src/analytics-script/index.ts:25-50`; [`Hiding your own traffic`](https://rybbit.com/docs/hiding-own-traffic#localstorage-method), [`JavaScript SDK`](https://rybbit.com/docs/sdks/web#opting-out)
- Rybbit's site settings say raw IP storage is disabled by default but can be enabled, and warn that enabling it is not GDPR compliant without a legitimate need and consent mechanisms. The source writes `ip` to event rows when `trackIp` is enabled. [`site-settings.mdx`](https://rybbit.com/docs/site-settings#track-ip-address), `rybbit/server/src/db/postgres/schema.ts:89-99`, `rybbit/server/src/services/tracker/pageviewQueue.ts:109-125`
- The privacy policy says IP addresses are never stored, while the site setting, source schema, and user-info API expose conditional IP storage. This is a direct official-material contradiction, not merely an inference about implementation. [`Privacy Policy`](https://rybbit.com/privacy#how-we-process-ips), `rybbit/server/src/db/clickhouse/schema/core.ts:115-125`, [`Get User Info`](https://rybbit.com/docs/api/users/info)`
- Identified user IDs are not anonymized by the browser tracker: the docs say they are stored exactly as supplied, and traits may contain email, name, and custom fields. That conflicts with the privacy policy's unqualified statement that Rybbit does not store personal data that could directly identify individuals. The identify documentation's consent warning is the more specific statement for this feature. [`identify-users.mdx`](https://rybbit.com/docs/identify-users#windowrybbitidentifyuserid-traits), [`Privacy Policy`](https://rybbit.com/privacy#gdpr-and-privacy-regulations-compliance)
- URL parameters are tracked by default, with a site setting to disable them when sensitive parameters may occur. Cimi should treat query strings, custom properties, traits, IP, and replay as separate data-classification decisions. [`site-settings.mdx`](https://rybbit.com/docs/site-settings#track-url-parameters), [`JavaScript SDK`](https://rybbit.com/docs/sdks/web#remote-configuration)

## Deletion semantics

- `clearUserId()` is logout/session-state cleanup, not erasure. It removes the browser's custom ID and stops future normal events from carrying that custom ID; it does not delete the server-side alias or previously attributed events. The current source also clears the replay recorder's user ID. [`identify-users.mdx`](https://rybbit.com/docs/identify-users#important-notes), `rybbit/server/src/analytics-script/tracking.ts:497-510`
- The source exposes an admin-only `DELETE /sites/:siteId/users/:userId` route. It finds all aliases for the identified user, deletes matching identified events plus unattributed events from linked devices, deletes session replay event/metadata-v2 rows and Cloudflare R2 replay batches, then deletes the profile and aliases. In a shared-device case, events already attributed to a different identified user are intentionally preserved. `rybbit/server/src/index.ts:373-376`, `rybbit/server/src/api/analytics/users/deleteUser.ts:16-24,29-83`
- The user-deletion handler's explicit table list is `events`, `session_replay_events`, and `session_replay_metadata_v2`; it does not issue deletes for `bot_events` or `bot_observations`. Therefore, the code's “all analytics data” erasure comment is broader than the tables visibly deleted in this handler. Whether those bot rows are in Cimi's personal-data scope is a policy decision, but it must be answered. `rybbit/server/src/api/analytics/users/deleteUser.ts:16-24,65-81`, `rybbit/server/src/db/clickhouse/schema/core.ts:141-239`
- Site settings promise that deleting a site permanently deletes all analytics data, reports, funnels, and goals. The current site deletion implementation deletes only session replay tables before deleting the PostgreSQL site row; it does not issue a delete for the main `events` table. The likely persistence of orphaned event rows is an inference from those two source paths, but the missing `events` deletion is a documented fact. [`site-settings.mdx`](https://rybbit.com/docs/site-settings#delete-site), `rybbit/server/src/services/sites/siteConfigurationLifecycle.ts:369-385`

## Explicit contradictions and interpretation risks

| Topic | Official statements | What Cimi should treat as authoritative pending verification |
| --- | --- | --- |
| Local storage | Privacy/security say no local storage; identify docs, SDK docs, and source persist IDs in local storage. | The source behavior is clear for identified/browser IDs. Do not inherit the privacy wording without scoping it to anonymous default tracking. |
| Raw IP | Privacy/DPA say IP is not stored; site settings and source allow `trackIp`, and the user-info API documents `ip`. | Default-off is evidenced; enabled behavior is raw IP persistence. Require an explicit deployment policy. |
| Backfill range | Identify docs say all past anonymous events; browser source limits routine backfill to 30 days; dashboard identify requests full history. | Model browser identify and operator identify as different operations, or verify the deployed version before promising full history. |
| Site deletion | Site settings promise all associated data is permanently deleted; source site deletion omits main events. | Do not promise erasure until ClickHouse events and all derived/replay/bot stores are verified. |
| Termination timing | DPA says 30 days; security page says 60 days after cancellation. | Treat as an unresolved service-contract contradiction, not a visitor deletion SLA. |

## Implications and questions for Cimi

- Should Cimi define anonymous identity as a durable client-generated ID, an IP/user-agent fingerprint, or a server-issued pseudonymous ID? Rybbit's browser implementation uses fingerprinting for normal events and local storage for an additional client ID.
- Are `visitor`, `anonymous identity`, `session`, `identified user`, `trait`, and `alias` separate records in Cimi's model, with explicit links and lifetimes?
- Does login backfill all history, a bounded window, or only events after identification? What happens when two people use one device, when identity changes, or when the backfill is delayed or fails?
- Is an identified user ID allowed to be an email or other direct identifier? If yes, what consent, access, correction, export, and erasure contract applies to traits and historical events?
- What is the consent boundary for anonymous tracking, IP storage, URL parameters, custom properties, session replay, and identification? Should the tracker be initialized only after consent, rather than relying on opt-out?
- Does logout only stop future association, or must it force a new session and remove any client-side anonymous/identified storage?
- What exact records must a deletion request remove: aliases, profiles, event rows, derived aggregates, replays and object storage, bot/audit rows, backups, and client storage? How is asynchronous backfill prevented from reintroducing deleted attribution?
- What retention is guaranteed per entity, and how are self-hosted configuration, Cloud plan windows, legal holds, and deletion completion exposed to Cimi users?
