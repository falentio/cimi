# Issue #52 acceptance audit: cross-resource admission integration

## Overview

Audit date: 2026-09-11.

This audit covers the cross-resource lifecycle seam, the subject of issue #52. It extends the issue #36 audit, whose scenarios are frozen in `docs/specs/ACCEPTANCE.md`. Every scenario in the `Lifecycle and Recovery` and `Event Acceptance` sections is marked `PASS`, `FAIL`, or `UNCOVERED` with a direct test reference.

A `PASS` requires an end-to-end HTTP test that asserts the documented observable behavior through `app.fetch`. A contract-only or repository-only test is not end-to-end coverage and is recorded as such, which is why several scenarios remain `UNCOVERED` even though their internals are tested below the HTTP boundary.

The reporting and public-disclosure runtimes that mount traffic, event, goal, funnel, cohort, and public-dashboard routers belong to issues #44 through #47, all of which remain open. Their shared-seam scenarios are `UNCOVERED` here by design and stay that way until those runtimes land.

## Composition root

`apps/api/src/index.ts` `createApiApp` is the single API composition root. It builds every resource module, composes their oRPC routers through `apps/api/src/orpc.ts`, and installs three client interceptors in order: error normalization, coarse authorization, and admission. The admission interceptor calls `resolveRequestAdmissionGate`, writes the ingestion admission onto the request context, then applies the gate by route class.

Route classes come from contract metadata. `packages/contract/src/orpc/meta.ts` defines `ADMISSION_VALUES` as `ingestion`, `analytics-read`, and `exempt`. The gate is resolved from `apps/api/src/health.ts` `resolveAdmissionGate`, which maps installation status and lifecycle admission mode onto ingestion and analytics-read decisions. `ADMISSION_EXEMPT_RESOURCES` in `index.ts` exempts `health`, `installation`, and `backupRestore` from the gate.

## Seam changes

`CreateApiAppDependencies` gained an optional `backupRestoreExecutor` field. It forwards to `createBackupRestore`, which already accepted an `executor` option. This lets an end-to-end test hold the backup and restore quiesced window open deterministically instead of racing a wall-clock executor. No production default changes: when the field is absent, the composition root builds the same `ConfiguredSqliteExecutor` as before.

`apps/api/src/testing/fixture.ts` gained two options. `analyticsReady` wraps the real test `AnalyticsDb` and overrides only `ready()`, so a test can model DuckDB unavailability while every other analytics call still hits real DuckDB. `backupRestoreExecutor` forwards the executor above.

## Remaining gaps

Six scenarios stay `UNCOVERED` at the HTTP boundary. Three depend on runtimes that issues #44 through #47 have not built: analytics read recovery, and the reporting freshness behavior behind it. Three are backup internals that only have repository-level tests: the pre-restore safety artifact, backup cleanup stages, and incompatible backup. The retention scenarios have HTTP coverage at the resource router layer, which is real HTTP through the composed app, but they are recorded as `UNCOVERED` here because that coverage predates this work and does not sit in the end-to-end suite.
