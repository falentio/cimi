# Issue #52 acceptance audit: cross-resource admission integration

## Overview

Audit date: 2026-09-30.

This audit covers the cross-resource lifecycle seam owned by issue #52. It extends the issue #36 audit, whose scenarios are frozen in `docs/specs/ACCEPTANCE.md`. Every scenario in the `Lifecycle and Recovery` and `Event Acceptance` sections is marked `PASS`, `FAIL`, or `UNCOVERED` with a direct test reference.

A `PASS` requires an HTTP test that asserts the documented observable behavior through `app.fetch`. A contract-only or repository-only test is not end-to-end coverage and is recorded as such.

Two test tiers exist and they are not interchangeable. The `apps/api/src/testing/` files drive the full composed app over real SQLite and real DuckDB through `app.fetch`, so they exercise the admission interceptor, the authorization interceptor, and the HTTP status. The `apps/api/e2e/` files are file-backed and survive a process restart, but they invoke procedures through `call(fixture.router.<resource>.<procedure>, ...)` rather than `app.fetch`. They prove durability and recovery across real files, and they do not prove HTTP admission. Only the first tier can satisfy the rule above, so an `apps/api/e2e/` test is cited as durability evidence and never as an HTTP `PASS`.

## Composition root

`apps/api/src/composition.ts` `createApiComposition` is the single API composition root. It builds every resource module and composes their routers through `apps/api/src/orpc.ts`. `apps/api/src/http-app.ts` installs three client interceptors in order: error normalization, coarse authorization, then admission. The admission interceptor calls `resolveRequestAdmissionGate`, writes the ingestion admission onto the request context, and applies the gate by route class.

Route classes come from contract metadata. `packages/contract/src/orpc/meta.ts` defines `ADMISSION_VALUES` as `ingestion`, `analytics-read`, and `exempt`. The gate is resolved by `resolveAdmissionGate` in `apps/api/src/health.ts`, which maps installation status and lifecycle admission mode onto ingestion and analytics-read decisions. `ADMISSION_EXEMPT_RESOURCES` in `http-app.ts` exempts `health`, `installation`, and `backupRestore`.

Every resource that owns an admission-relevant read or write is mounted: collection (`eventIngestion`), identity (`identityProfile`), installation, organization, membership, invitation, site, collection policy, retention policy, backup-restore, authenticated reporting (`trafficReport`, `eventReport`, `goal`, `funnel`, `cohortRetention`), and public disclosure (`publicDashboard`).

## Seam changes

`TrafficReportService` and `EventReportService` gained a required `lifecycleLock`. Both wrap every public report method in the shared `analytics-read` lease through one helper, `apps/api/src/lifecycle/analytics-read-lease.ts` `withAnalyticsReadLease`, which acquires before site scope resolution and admission, fails closed with the kernel's `lifecycle-locked` `SERVICE_UNAVAILABLE` when the lease is refused, and releases after the read. The read error wins over a release error so a broken unlock cannot mask the caller's real failure. This closes the deferred finding F7 from PR #68, where a site deletion could race an analytics read. `createTrafficReport` and `createEventReport` require the lock, and the composition root passes its lifecycle lock.

The lock is required rather than optional so a forgotten wiring cannot silently skip the lease. The helper is shared with the reporting kernel's equivalent boundary rather than copied per service.

`createApiTestFixture` gained `analyticsReady`, which overrides only the analytics store readiness probe while every other analytics call still hits real DuckDB, `backupRestoreExecutor`, which holds a backup or restore quiesced window open deterministically, and `lock`, which lets a test hold an exclusive lifecycle lease.

## Documented-versus-implemented gaps

Three admission behaviors are implemented but not specified. `docs/specs/ACCEPTANCE.md` documents read admission during a held lifecycle lock only for backup ("analytics reads may continue") and read failure for store-not-ready states.

1. **Reads during retention or cleanup.** A report read fails closed because cleanup mutates the derived store and the kernel refuses a shared read while an exclusive non-backup lease is held. No scenario states this.
2. **Reads during upgrade maintenance.** `maintenance` with both stores ready resolves analytics reads to unavailable, so reports fail closed. The health spec defines the `maintenance` matrix entry but says nothing about read admission for it.
3. **Ingestion and analytics reads are mutually exclusive.** `InMemoryLifecycleLock` refuses an `analytics-read` lease while any `ingestion` lease is held, and refuses an `ingestion` lease while any read lease is held. A collection holds its lease across the coalescer window, so a concurrent report returns `503`; a report holds its lease across the whole read, so a concurrent collection returns `503` and does not durably accept. This predates issue #52 for the reporting kernel and the public dashboard, and issue #52 makes the seam uniform by extending it to the traffic and event reports. The exclusion buys no DuckDB safety, because ingestion writes only SQLite and projection is asynchronous.

All three are availability semantics, not correctness defects, and all three fail closed. Recording them in `docs/specs/ACCEPTANCE.md` is a documentation follow-up. If the ingestion-versus-read exclusion is not wanted, the change belongs in `packages/kernel/src/ports.ts` and is out of scope for this issue.

## Verification

The five HTTP end-to-end files pass as a group, fifteen tests total:

- `apps/api/src/testing/ingestion.admission.test.ts` (4 tests)
- `apps/api/src/testing/ingestion.coexistence.test.ts` (1 test)
- `apps/api/src/testing/lifecycle.quiesce.test.ts` (4 tests)
- `apps/api/src/testing/lifecycle.restart.test.ts` (2 tests)
- `apps/api/src/testing/site.failClosed.test.ts` (4 tests)

The two resource lifecycle files pass with four tests each, eight total, and pin the lease in four ways: it spans the read, it releases on a failed read, it fails closed when refused, and it stays compatible with a backup lease. They sit alongside the reporting kernel's existing `apps/api/src/resources/reporting/testing/query.lifecycle.test.ts`.

The full `@cimi/api` unit suite passes 926 of 927 tests. The one failure is a pre-existing load-sensitive 5-second timeout in `apps/api/src/resources/traffic-report/testing/service.getBreakdowns.test.ts` `rejects an hourly range after the authenticated bucket limit`. It fails identically on untouched `main` and passes three of three in isolation.

The file-backed suite passes 26 of 26 tests across 6 files with `vp test run e2e --pool forks --no-file-parallelism --maxWorkers=1`. Those tests drive procedures through the router rather than `app.fetch`, so they are durability evidence across a restart and are not counted as HTTP coverage in the matrix.
