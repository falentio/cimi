## The one failure, in detail (item 2)

Reproduce: `vp test run .audit/verify-164-round2/c23-probe.test.ts` -> `/tmp/verify-164-round2/out/c23-probe.json`.

1. The seed's first retention-cleanup pass runs while the projection append is open. At 21,186 ms the installation row reads `derived_cleanup_status = 'running'`, `backup_cleanup_status = 'pending'`.
2. `readStoreHealth` (`apps/api/src/health.ts:203-228`) reports `cleanupPending: true`; `resolveInstallationHealth` (`health.ts:53-62`) returns `degraded` even though `analyticsStore: ready`.
3. `resolveAdmissionGate` (`health.ts:97-115`) maps `degraded` to `analyticsReads: 'unavailable'`; the analytics-read interceptor (`apps/api/src/http-app.ts:108`) throws `admissionUnavailable` (`http-app.ts:412-418`). The 503 body carries exactly that stack.
4. Measured degraded window: 3 consecutive health samples at 250 ms spacing (12,318-12,853 ms in out/c23-final.json; 20,999-21,837 ms in out/c23-probe.json). The append window is far wider (8.7-15.4 s), and queries later in it return 200. So the residual defect is a start-of-seed window, not the whole append.

This is not analytics readiness: `analytics.ready()` returned true in every sample of these runs (0 false in 1,720 samples across six runs, excluding the by-design `rebuilding` window of an explicit `rebuild()` call). The round-1 finding (F1) named `ready()` false during the append; that half is fixed, and the remaining 503 comes from the installation cleanup gate instead.

## Other observations the fixer did not mention

1. **`ready()` probe walls up to 20.7 s.** In the same run: `readiness.slowProbes` = 20,677 ms (call started 60 ms after the ensure, returned true when the append began), 3,938 ms, 1,787 ms (out/c23-probe.json). Because the seed runs in-process, this may be event-loop starvation rather than a DuckDB stall; the harness cannot separate the two. It matters because `readStoreHealth` awaits this probe on every non-exempt request, so a request arriving in that window waits on it. Not claimed by the branch.
2. **F3 (partial-cardinality read) is still observable and still accepted.** A checkpoint still publishes `readiness: 'ready'` with a partial cardinality: the mid-append query at 12.4 s returned 1,064 visitors / 1,762 sessions, versus 1,825 / 4,888 at the end (out/c23-final.json). The branch records this as an accepted risk (commit 669fe5a2).
3. **`rebuild()` takes analytics reads offline for its duration by design.** Every F2-style run shows ready() false only inside the explicit rebuild window (57/670 in the reported run; 0/532 outside), and the same was true for 78/619 and 86/670 in the two earlier attempts. Nobody should read a false `ready()` during a rebuild as a regression.
4. **The F2 fix has two independent layers.** `readProperties` now chunks pks by 900 (`packages/db/src/duckdb/projection-source.ts:191-228`), which is what makes an installation-wide rebuild succeed; and the cleanup's rebuild is now gated on `hasPendingIdentityRedactions(db, siteId)` (`apps/api/src/resources/retention-cleanup.ts:120-129`), which is why the worker made 0 rebuild calls in a two-site installation where it previously looped. Either layer alone removes the observed loop; only the first fixes the variable-cap root cause.
5. **`ready()` still bypasses the serial chain.** The only change in `packages/db/src/duckdb/index.ts` between 8c332b64 and this head is the added `console.error` in the `catch` (line ~279); `ready()` still runs its queries outside `enqueue` (`index.ts:249-282`). The F1 improvement came from the append/cleanup side, not from making the probe share the serial chain.
6. **The e2e's inner poll budget is 30 s while observed seed+projection times are 13-42 s.** The branch's new e2e waits through `fixture.waitFor` with a 30,000 ms default (apps/api/e2e/fixture.ts:282-283). My c23-probe run took 42.0 s from ensure to convergence (the host was busy at 99% disk); a repeat of that under CI would fail the e2e even though the product is fine. The 90-day e2e passed here in 17.65 s, so this is a flakiness risk, not a current failure.
7. **Second-site discovery in round 1's F2 harness is ambiguous.** `select id from site order by created_at desc limit 1` returned the first site in my first two attempts, which silently mislabeled which site the reads belonged to. I switched to a before/after id diff (out/f2-round2.json `allSites` / `sitesAtEnd` show both rows). The round-1 report's F2 numbers used the ambiguous selector.
8. **`secondState` is a sampling instant, not the end state.** In the reported F2 run the second site was still projecting when sampled (`converged: false`, checkpoint cardinality 12,500 vs accepted 26,979); by the end of the run total DuckDB events = total accepted = 55,104. The 8 post-rebuild reads were fired while that site finished projecting and all returned 200.
